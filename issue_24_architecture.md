Issue #24

## 1. Цель задания

Исследовать и реализовать `Precision@k` и `Recall@k` для оценки векторных представлений хостов как задачи поиска похожих хостов.

Главное правило: релевантные соседи определяются независимо от векторного представления, которое сейчас оценивается.

---

## 2. Место метрик в общей архитектуре

```text
Единый эталон
       |
       +-- pairs.csv
       |
       v
+-------------------+
|   Модуль оценки   |
+---------+---------+
          |
          | pairs.csv
          v
embeddings.csv
          |
          v
  Ранжирование при поиске
          |
          +---- Precision@k
          |
          +---- Recall@k
```

`embeddings.csv` содержит векторное представление конкретного метода.

`pairs.csv` содержит общую эталонную разметку бенчмарка.

Поэтому разные методы проходят через один и тот же контракт оценки.

---

## 3. Общий формат векторных представлений

Модуль оценки получает:

```text
host_id | emb_1 | emb_2 | ... | emb_n
```

`host_id` используется как ключ.

Нельзя считать, что строки разных файлов соответствуют друг другу по позиции.

---

## 4. Единый эталон релевантности

Для P@k/R@k используется:

```text
reference/pairs.csv
```

с форматом:

```text
host_a | host_b | label | split
```

где:

```text
label = 1 -> релевантный
label = 0 -> нерелевантный
```

Это фиксированное определение релевантных соседей.

Критически важно:

> релевантные соседи нельзя определять отдельно для каждого векторного представления через его собственных ближайших соседей или кластеризацию.

Иначе разные методы будут оцениваться по разной эталонной разметке.

---

## 5. Поиск похожих хостов

Для каждого хоста:

```text
1. Берём векторное представление хоста.
2. Считаем косинусное сходство с векторными представлениями других хостов.
3. Исключаем самого себя.
4. Сортируем кандидатов по сходству.
5. Берём top-k.
6. Сравниваем найденные пары с эталонными релевантными парами из pairs.csv.
```

Значения `k` берутся из:

```text
benchmark/config.json
```

Сейчас задаются:

```text
k = 5
k = 10
k = 20
```

---

## 6. Precision@k

Для одного исходного хоста:

```text
Precision@k =
число релевантных хостов среди top-k
-------------------------------------
k
```

Метрика отвечает на вопрос:

> насколько большая часть найденных top-k соседей действительно является релевантной согласно единому эталону?

---

## 7. Recall@k

Для одного исходного хоста:

```text
Recall@k =
число релевантных хостов среди top-k
-------------------------------------
общее число релевантных хостов
```

Метрика отвечает на вопрос:

> какую долю всех известных релевантных соседей нам удалось найти среди top-k?

---

## 8. Особые случаи

Модуль оценки должен использовать общий контракт оценки и корректно работать с ситуациями:

- хост есть в `embeddings.csv`, но отсутствует в эталоне;
- есть дублирующийся `host_id`;
- `k` больше количества доступных кандидатов;
- у хоста нет релевантных соседей;
- часть записей в `pairs.csv` относится к другой части данных.

При этом модуль оценки не должен молча создавать новый эталон или новое случайное разделение данных.

---

## 9. Разделение данных

P@k/R@k должны использовать фиксированную тестовую часть данных из единого эталона.

То есть логика выглядит так:

```text
pairs.csv
   |
   +-- train
   +-- validation
   +-- test
             |
             v
        P@k / R@k
```

Новое случайное разделение внутри самой метрики не создаётся.

Это важно для того, чтобы все методы оценивались на одинаковой задаче.

---

## 10. Связь с нашей лестницей экспериментов

P@k/R@k сами по себе не определяют временную схему.

Они используют то разделение данных, которое задано единым эталоном.

Поэтому возможны разные уровни строгости.

### E0

```text
T -> векторное представление
T -> эталонные пары
```

Это минимальная проверка сохранения структуры.

### Более строгий временный эксперимент

```text
T1 -> векторное представление

T2 -> эталонные пары / тест
```

Здесь P@k/R@k уже проверяют, насколько векторное представление, построенное на T1, сохраняет способность находить релевантных хостов на T2.

Таким образом, сама метрика остаётся одной и той же, а эксперимент становится строже за счёт временной схемы.

---

## 11. Стабильность по k

Нужно проверить результаты для нескольких значений:

```text
k = 5
k = 10
k = 20
```

Это позволяет увидеть, как меняется качество поиска при увеличении числа возвращаемых соседей.

Не нужно подбирать `k` отдельно под каждый метод.

Все методы получают одинаковые значения из:

```text
benchmark/config.json
```

---

## 12. Связь с другими метриками

P@k/R@k отвечают на вопрос о поиске похожих хостов.

Они не заменяют:

- `knn_consistency` — проверку совпадения локальных соседств с независимым эталонным пространством признаков;
- `triplet_accuracy` — проверку относительного порядка положительного и отрицательного примеров;
- `pairwise_roc_auc` и `pairwise_pr_auc` — оценку качества различения пар хостов;
- `linear_probe` — проверку наличия информации о целевом признаке в векторном представлении.

Все эти метрики используют общий контракт оценки.

```text
                      |
                      v

                      |

       |              |              |

   P@k / R@k       kNN          линейная проверка

       +-- k=20
```

## 14. Главный принцип оценки

Нельзя делать:

```text
метод A -> свои релевантные соседи
метод B -> свои релевантные соседи
```

Нужно:

```text
                    pairs.csv
                       |
             +---------+---------+
             |         |         |
             v         v         v
         метод A    метод B    метод C
             |         |         |
             +---------+---------+
                       |
                       v
                 одинаковая оценка
```

Тогда разница в P@k/R@k действительно отражает разницу между векторными представлениями, а не разницу между способами построения эталона.

---

Все критерии выполнены:

- определена релевантность независимо от оцениваемого векторного представления;
- используется общий `reference/pairs.csv`;
- реализованы `Precision@k` и `Recall@k`;
- используются значения `k` из `benchmark/config.json`;
- проверены несколько значений `k`;
- используется фиксированная тестовая часть данных;
- одинаковый контракт оценки применяется ко всем методам;
- есть небольшой понятный пример расчёта;
- подготовлены краткие описание метода, реализации и результатов.

Главное требование интеграции:

```text
embeddings.csv + reference/pairs.csv + фиксированное разделение
```

а не отдельный эталон для каждого метода.
