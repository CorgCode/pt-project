# Методология и проверка валидности

Статус: пайплайн, метрики и аудит реализованы и покрыты тестами; **все числа ниже получены на синтетике в формате LANL**
(`python -m pipeline.fixtures`, seed 0, 300 хостов) и показывают протокол, а не поведение сети. Настоящие данные LANL
пока недоступны. Каждый прогон помечен `synthetic_fixture`, `unverified` (по умолчанию для любых других данных) или
`lanl_declared` (заявление оператора с указанием источника); происхождение **никогда не проверяется** пайплайном,
и отчёты пишут, какая пометка действует. Выводы по синтетике или непроверенным данным — не выводы о LANL.

## 1. Вопрос и границы

Можно ли по эмбеддингу хоста, построенному по *более раннему* окну трафика, находить похожие хосты, предсказывать
будущие связи и узнавать хост снова? Метки ролей бенчмарк **не** требует: для LANL NetFlow их нет, и мы их не придумываем.
Каждая метрика говорит, что именно она измеряет, и смешивать их нельзя:

| вид | откуда суждение | что значит высокий результат |
|---|---|---|
| поведенческое соседство (kNN) | поведенческий профиль хоста в более позднем окне | соседи в эмбеддинге совпадают с теми, кто позже ведёт себя похоже (**приближение**) |
| будущие связи | реально ли пара общается позже | эмбеддинг помогает **предсказывать** общение |
| собеседники через похожих | новые собеседники хоста позже | похожие хосты подсказывают, с кем хост начнёт общаться |
| узнаваемость | тот же `host_id` в двух окнах | эмбеддинг стабилен **и** различает хосты во времени |
| общие собеседники (пары, тройки, P@k/R@k) | пересечение собеседников в более позднем окне | эмбеддинг согласуется со **структурным приближением** |
| линейный зонд | внешние метки с указанным источником | внешнее свойство читается линейно (без меток недоступно) |

## 2. Протокол данных и защита от утечки

* Источник: LANL Unified Host and Network Dataset (2017), NetFlow; схема — `pipeline/README.md`.
* Окна `train < validation < test` — полуинтервалы, по порядку, без пересечений (проверяется); потоки, идущие
  на границе окна, выбрасываются.
* **Когорта** (решается до моделей; см. 4.9). По умолчанию `train_only`: хосты, активные в train; в позднем окне
  оцениваются только активные там, покрытие пишется в отчёт. Старая политика `all_windows` (активны во всех окнах)
  позволяет будущему решать, кто оценивается, — это бенчмарк «стабильных хостов».
* **Происхождение** (`pipeline/provenance.py`): данные `unverified`, пока не заявлено иное; заявление LANL требует
  указания источника, имён файлов как у LANL и отсутствия маркера/подписи синтетики.
* Модели читают только `ProcessedData.training_flows()/training_graph()`. Для встроенных методов это проверяет тест:
  во время `fit()` чтение любого окна, кроме train, падает (`benchmark/baselines/test_temporal.py`). Внешние методы
  проверить кодом нельзя — они должны заявить окно обучения.
* Эталоны строятся только по более позднему окну (`validation`, `test`); параметры и решения анализа принимаются
  на `validation`, итоговые числа — на `test`.
* Обученный классификатор связей учится на кандидатах validation и оценивается на test; иначе — отказ.
* Таблица результатов отказывается смешивать разные эталоны (у каждого файла SHA-256), когорты, split и синтетику
  с реальными данными.

## 3. Независим ли эталон от оцениваемого эмбеддинга?

Эталоны строятся из сырых логов более позднего окна, никогда — из эмбеддинга. Но **информация** может пересекаться
по построению: вход метода и источник эталона похожи. Аудит записывает это явно (`experiments/audit.py::OVERLAP`,
печатается в каждом отчёте):

| метод | поведенческие соседи | будущие связи | общие собеседники |
|---|---|---|---|
| random | нет | нет | нет |
| behavioral / PCA / SVD | те же признаки, более раннее окно | нет | слабо (поведение связано с собеседниками) |
| graph_spectral и графовые методы | слабо (степень видна в спектре) | **сильно** (связи сохраняются) | **сильно** (собеседники сохраняются) |
| reference_ceiling | совпадает по построению | нет | слабо |

Следствия: бейзлайны — точки калибровки, а не независимое доказательство; хороший прогноз связей у графового
эмбеддинга во многом объясняется *сохранением связей* (4.5); хороший результат поведенческих признаков на
поведенческом эталоне в основном измеряет *сохранение поведения во времени*. Обученную модель нужно сравнивать
с этими бейзлайнами, а не только со случайным уровнем.

## 4. Проверки валидности (реализованы, запускает `experiments.run_experiment`)

**4.1 Чувствительность к весам признаков.** Поведенческий эталон зависит от весов блоков (объём, степень, направление,
порты, протоколы, час суток). Аудит пересобирает эталон с 12 случайно изменёнными векторами весов (каждый вес
×exp(N(0,0.5)); в трети конфигураций один блок убран) и сообщает (i) совпадение соседей с основным эталоном и
(ii) тау Кендалла порядка методов. Синтетика: совпадение соседей в среднем 0.74 (минимум 0.58; случайно 0.033); тау порядка методов в среднем 0.92, минимум 0.86.
Вывод: эталон умеренно устойчив, но *порядок близких методов* может меняться с весами — небольшие разницы
между почти равными методами не стоит переоценивать.

**4.2 Стабильность во времени.** Consistency@10 между поведенческими соседями двух разных окон (синтетика:
train→test 0.28, train→validation 0.28, validation→test 0.33; случайно 0.033). Это ориентир, чего вообще можно ждать
от эмбеддинга раннего окна на kNN-метрике: поведенческий бейзлайн — это и есть «сохранение» — набирает 0.28.
Модель, которая заметно его не превосходит, не показала ничего сверх того, что поведение просто сохраняется.

**4.3 Случайный уровень.** 30 случайных эмбеддингов оцениваются на test-эталоне (`audit.json:random_null`).
Синтетика: kNN 0.034±0.003, AUC связи (косинус) 0.501±0.007, AUC пар 0.501±0.021, тройки 0.502±0.023.
Значимость судим по этим полосам, а не по 0.5.

Бутстреп-интервалы (`--bootstrap`). Пары и тройки **делят хостов**, поэтому их пересэмплирование как независимых
занижает разброс. Для связей, пар и троек используется **бутстреп по хостам**: хосты пересэмплируются с возвратом,
элемент получает вес — произведение кратностей своих концов. В симуляции с эффектами хостов
(`evaluation/test_host_bootstrap.py`) номинальный 95% интервал бутстрепа по парам накрывал истинный AUC в 70% случаев
и был вдвое уже, а бутстреп по хостам — в 97%. Для kNN и Precision@k пересэмплируются хосты. Интервалы описывают
только выбор оцениваемых элементов — не seed модели, не выбор эталона и не выбор окон.

**4.4 Доля положительных среди кандидатов.** Выборка кандидатов сбалансирована (50% положительных), а настоящая доля
мала (синтетика: 0.083). Поэтому PR-AUC на выборке — не PR-AUC «в бою». Оценка пишет lift PR-AUC (AP / доля в выборке),
PR-AUC, *пересчитанный к настоящей доле*, и саму долю. Пересчёт исправляет только долю классов, **но не то, какие**
отрицательные выбраны: случайные пары без связи — лёгкие, поэтому абсолютные значения оптимистичны. Для пар по общим
собеседникам см. 4.8: там пересчёт идёт к доле **среди размеченных** пар — это условная величина.

**4.5 Сохранение связей и почему сырой косинус — плохой прогноз связи.** 51% будущих связей уже были в source-окне.
Тривиальный прогноз «пара уже общалась» даёт ROC-AUC 0.708 и сохраняется рядом с каждым результатом. Косинус эмбеддингов
даёт ≈0.47–0.49 у поведенческих методов: в трафике «клиент–сервер» связанные хосты непохожи, а похожие клиенты одной
роли (никогда не связанные) попадают в отрицательные. Если смотреть только на косинус, можно ошибочно решить, что
эмбеддинги ничего не знают о связях. Поэтому оценка показывает ещё классификатор рёбер на `[|e_a−e_b|, e_a∘e_b]`,
обученный на кандидатах validation и оцененный на test (синтетика: граф 0.730, поведение 0.668, случайный 0.546 против
0.708 у «уже общались»). **У случайного эмбеддинга обученная оценка выше 0.5** (полоса 0.543±0.007): случайный вектор
работает как идентификатор хоста, и классификатор запоминает хабы. Обученную оценку всегда читаем относительно строки
random; отдельно показываются только новые связи.

**4.6 Выравнивание окон.** Эмбеддинги, обученные на каждом окне отдельно (например graph_spectral), поворачиваются
между окнами; сырой косинус между окнами тогда бессмыслен (синтетика: Top-1 0.000 против 0.180 после Procrustes).
Узнаваемость подбирает поворот на половине хостов (по seed) и оценивает на другой половине, так что оцениваемые хосты
не влияют на выравнивание; сырой результат осмыслен только для методов с одной системой координат. Ничьи считаются
точным матожиданием, поэтому константный эмбеддинг ровно на случайном уровне. Procrustes может «съесть» и систематический
дрейф метода с общими координатами (поведение 0.047 → 0.133), так что два числа отвечают на разные вопросы.

**4.7 Согласие порядка между split.** Тау Кендалла между порядком методов на validation и test по каждой метрике (синтетика, 11 методов: kNN 0.89, AUC пар 0.78, тройки 0.90, косинус связи 0.70).
Где все методы около случайного уровня (косинус связи), порядок — шум, и тау ≈ 0 ожидаемо.

**4.8 Неполная разметка пар и что такое «доля» для пар.** Пары размечаются фиксированным правилом (Jaccard собеседников
≥ τ — похожи, = 0 — не похожи, между — **не размечены**). Неразмеченные пары никогда не считаются «непохожими»;
P@k/R@k работают по размеченным кандидатам и пишут покрытие, лучший возможный и случайный уровень на тех же хостах.
Доля похожих по размеченным счётчикам, `judged_population_prevalence` = похожие / (похожие + непохожие), **условна**:
это не доля среди всех пар хостов (`population_positive_rate` = похожие / все пары, пишется рядом с `unjudged_share`;
синтетика: 0.070 против 0.010, 86% пар не размечены). Поэтому `pair_pr_auc_at_judged_prevalence` — AP по размечаемым
парам, а не по всем. (Ревью #50; регрессионные тесты — `evaluation/test_prevalence_semantics.py`.) Для будущих связей
каждая пара либо общалась, либо нет, поэтому там настоящая доля определена — с оговоркой, что «потока не было» не значит
«связь невозможна».

**4.9 Отбор когорты и покрытие.** При старой политике `all_windows` хост попадает в бенчмарк, только если активен
в validation *и test*, то есть будущее влияет на отбор: результаты завышают сохранение, узнаваемость и сохранение связей.
Политика по умолчанию `train_only` это убирает: когорта определяется по train, а «выживание» в позднее окно — часть
измеряемого; неактивный в окне хост там просто не оценивается, отчёт пишет покрытие и диагностику выживания. Не покрыто:
хосты, появившиеся позже, и метрики по исчезнувшим хостам.

**4.10 Воспроизводимость.** Всё с seed (`--seed`); `experiments/test_protocol.py` запускает весь эксперимент дважды
и проверяет, что все JSON/CSV/Markdown совпадают (кроме git SHA), что случайный бейзлайн меняется с seed, а
детерминированные — нет, и что оцениваемые эмбеддинги не зависят от потоков validation/test. Версии библиотек — в
`manifest.json`; побитового совпадения на других версиях не обещаем.

**4.11 Внешние методы.** Происхождение обучения кодом не проверить. Можно приложить `provenance.json`
(`{"trained_on_windows": ["train"]}`); заявление с более поздним окном отклоняется, отсутствие — помечается в отчёте.

**4.12 Бейзлайн без портов и абляция признаков (#43).** В поведенческом профиле шесть блоков (volume, peers, ratio,
ports, proto, hourly); из полей портов строится только `ports`. `exclude_blocks=("ports",)` убирает блок полностью
(тест перемешивает колонку портов — признаки без портов не меняются бит в бит). `python -m experiments.feature_ablation`
сравнивает `full`, `no_ports` и все варианты «минус блок» на **одних** хостах, окнах и эталонах с парными интервалами.
* Стандартный kNN-эталон *содержит* блок портов (~18% квадрата веса профиля), поэтому полный бейзлайн делит с ним
  информацию по построению; разница на kNN — это пересечение, а не качество представления. Эталоны пар, троек и связей
  портов не содержат — там абляция показывает, что дают сервисы для структуры и прогноза.
* Диагностика пересобирает kNN-эталон без портов (только анализ: другой отпечаток, в таблицу не попадает).
* Только синтетика, где порты информативны **по построению**: полный против без портов — kNN@10 0.280 против 0.272
  (разность +0.008, 95% CI [−0.000, +0.016]); AUC пар 0.907 против 0.885 (+0.022 [+0.006, +0.042]); косинус связи
  0.478 против 0.457 (+0.021 [+0.015, +0.027]); тройки 0.918 против 0.887 (+0.031 [0.000, +0.072]). Против эталона
  без портов у полного бейзлайна преимущества нет (−0.004 [−0.013, +0.004]). Для LANL, где редкие порты обезличены,
  отсюда ничего не следует.

сигнал. PCA и SVD совпадают, потому что признаки уже центрированы. О LANL отсюда ничего не следует.

## 6. Угрозы валидности и ограничения

* Только синтетика; величина эффектов на реальном трафике неизвестна.
* Происхождение настоящих файлов — заявление, а не проверка (контрольных сумм нет).
* Поведенческий эталон и разметка по общим собеседникам — *наши* определения похожести.
* Случайные отрицательные делают прогноз связей легче, чем с «трудными» отрицательными.
* В признаках используются счётчики инициатора; счётчики получателя сохраняются, но не используются.
* У `Time` нет документированного начала, поэтому «час суток» — относительно неизвестного начала отсчёта.
* Происхождение обучения внешних методов кодом не проверить.
* Интервалы не покрывают разброс по seed обучаемых моделей.
* P@k/R@k работают на маленьких выборках кандидатов (k ≤ 5); τ для пар подбирается по данным (пишется в манифест).

## 7. Что нужно для настоящего эксперимента

1. Файлы LANL `netflow_day-NN.bz2` (форма скачивания; ссылки одноразовые) и машина для обучения.
2. `describe`, объявить окна в единицах `Time`, запустить `pipeline.prepare` (с `--data-kind lanl --source-note ...`,
   иначе прогон `unverified`) и `pipeline.reference`.
3. `python -m experiments.end_to_end --netflow ... --config ... --workdir runs/lanl --methods all`.
4. Если появятся внешние метки хостов — `--labels F --labels-source "..."` включит зонд.

Что можно утверждать по такому прогону: порядок методов на *этих* эталонах с перечисленными оговорками.
