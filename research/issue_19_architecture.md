Issue #19

## 1. Цель задания

Подготовить единый и воспроизводимый конвейер данных и графа, которым смогут пользоваться все методы построения векторных представлений хостов.

Главная идея: все методы должны работать с одной согласованной системой `host_id` и оцениваться на одних и тех же общих эталонных файлах.

---

## 2. Общая архитектура

```text
Исходные данные LANL
       |
       v
Предобработка
       |
       +-- стабильные host_id
       +-- временное окно
       +-- очищенные/агрегированные данные
       |
       +------------------------+
       |                        |
       v                        v
Данные для построения      Единый эталон
векторного представления       |
       |                       +-- features.csv
       v                       +-- pairs.csv
Граф / вход метода            +-- triplets.csv
                             +-- labels.csv
```

Дальше каждый метод получает свои входные данные, но результат должен быть приведён к общему формату `embeddings.csv`.

```text
Метод построения векторного представления
       |
       v
embeddings.csv
       |
       v
Общий модуль оценки
       |
       v
Метрики бенчмарка
```

---

## 3. Что делаем с исходными LANL-данными

Исходные данные проходят единую предобработку.

На этом этапе необходимо:

- определить и документировать правила предобработки;
- сохранить стабильный `host_id`;
- определить и документировать временные окна;
- получить единое представление хостов;
- построить исходный граф хостов, который затем может использоваться методами построения векторных представлений.

Точные длины временных окон заранее не придумываются. Они должны быть частью экспериментального дизайна и зафиксированы в документации.

---

## 4. Граф хостов

Граф рассматривается как вход для методов построения векторных представлений.

Базовая идея:

```text
host = узел
network interaction = ребро
```

То есть:

- **узел** — хост;
- **ребро** — связь между двумя узлами, возникающая из сетевого взаимодействия между хостами.

Например, если в исходных сетевых событиях есть взаимодействие `Host A -> Host B`, при построении графа оно может быть представлено ребром между узлами `Host A` и `Host B`.

При необходимости у ребра могут сохраняться дополнительные характеристики взаимодействия, например агрегированные характеристики событий. Конкретный набор таких характеристик не следует придумывать, если он не задан техническим заданием.

**Построение графа** — это правило, которое определяет, какие сетевые взаимодействия становятся рёбрами графа и в каком виде они сохраняются.

Главное требование — одинаковый и воспроизводимый способ построения графа для соответствующего эксперимента.

Граф сам по себе не является эталонной разметкой для оценки.

---

## 5. Единый эталон

По требованию тимлида необходимо подготовить общие эталонные файлы.

Все методы должны сравниваться с одними и теми же файлами.

### `reference/features.csv`

Независимое эталонное представление хостов.

Минимальный формат:

```text
host_id | ref_1 | ref_2 | ... | ref_n
```

Требования:

- уникальный `host_id`;
- числовые эталонные признаки;
- отсутствие `NaN` и `Inf`;
- эталонное представление не должно строиться из оцениваемого векторного представления.

Используется, например, для `knn_consistency`.

### `reference/pairs.csv`

```text
host_a | host_b | label | split
```

Где:

- `label = 1` — похожие / релевантные;
- `label = 0` — отличающиеся / нерелевантные;
- `split` определяет принадлежность пары к нужной части эксперимента.

Этот файл является общим эталоном для парных метрик и метрик поиска похожих хостов.

### `reference/triplets.csv`

```text
anchor | positive | negative | split
```

Используется для `triplet_accuracy`.

### `reference/labels.csv`

```text
host_id | target | split
```

Используется для линейной/логистической проверки векторного представления.

Если проекту потребуется несколько целевых признаков для такой проверки, они должны быть явно определены в структуре бенчмарка, а не создаваться отдельно для каждого метода.

---

## 6. Разделение данных по времени

Временное разделение и разделение на обучение/проверку/тест — связанные, но разные понятия.

- **временное разделение** отвечает на вопрос «когда были получены данные»;
- **обучение/проверка/тест** отвечает на вопрос «какую роль эти данные выполняют в эксперименте».

Для временных экспериментов предпочтительная схема:

```text
T1 = окно обучения / построения эталона
T2 = окно проверки, если нужно
T3 = отложенное тестовое окно
```

Точная схема должна быть зафиксирована до эксперимента.

Важно не подбирать число окон под полученный результат.

---

## 7. Лестница экспериментальной сложности

Наша идея используется как схема проверки. Это не отдельная сложная система, а несколько заранее определённых экспериментов с постепенно возрастающей строгостью.

### E0 — минимальная строгость

```text
T
|
v
векторное представление
|
v
векторное представление(T)
|
v
целевой признак(T)
```

Это контрольный эксперимент на сохранение структуры.

Он отвечает на вопрос:

> содержит ли векторное представление информацию, связанную с целевым признаком, если проверка проводится в максимально благоприятных условиях?

Успех здесь не доказывает временное обобщение.

### E1 — независимое эталонное представление

```text
          T
          |
     +----+----+
     |         |
     v         v
векторное   эталон
представление |
     |         |
     v         v
embeddings   features
     |         |
     +----+----+
          |
          v
    метрики структуры
```

Здесь проверяется сохранение структуры относительно заранее определённого эталона.

### E2 — временное обобщение

```text
T1
 |
 v
векторное представление
 |
 v
embeddings(T1)

T2
 |
 v
эталон / тест
```

Теперь проверяется, переносится ли информация на другой временной период.

Это более строгая проверка, чем E0.

### E3 — временная устойчивость

Если это потребуется отдельным экспериментом:

```text
T1 -> векторное представление
       |
       +-> T2
       +-> T3
       +-> T4
```

Добавлять такую схему в основной конвейер без необходимости не нужно.

---

## 8. Почему E0 нужен

E0 не заменяет временное обобщение.

Он нужен как контрольная точка:

> сначала проверяем, что векторное представление вообще способно сохранить нужную информацию; затем увеличиваем строгость и проверяем переносимость.

Получается последовательность:

```text
наличие информации
        ->
сохранение структуры
        ->
переносимость
        ->
временная устойчивость
```

---

## 9. Воспроизводимость

Конвейер должен быть воспроизводимым из документированных исходных данных.

Необходимо обеспечить:

- стабильные `host_id`;
- одинаковые правила предобработки;
- документированные временные окна;
- документированный способ построения графа;
- детерминированную обработку или фиксированный `seed`, где это применимо;
- одинаковые общие эталонные файлы для всех методов.

---

## 10. Что должно получиться

Минимальный результат задания:

```text
исходные данные LANL
   ->
предобработка
   ->
стабильные host_id
   ->
временное окно
   ->
граф хостов / вход метода
   ->
единый эталон
```

И должны существовать или воспроизводимо получаться:

```text
reference/features.csv
reference/pairs.csv
reference/triplets.csv
reference/labels.csv
```

плюс документированное разделение данных.

---

Все критерии выполнены: 

- конвейер воспроизводится из документированных исходных данных;
- `host_id` совпадает между исходными данными, графом, векторными представлениями и оценкой;
- временные окна документированы;
- способ построения графа документирован;
- подготовлен небольшой обработанный пример или воспроизводимый способ его получения;
- общие эталонные файлы одинаковы для всех методов;
- эталон не строится из оцениваемого векторного представления;
- разделение данных фиксировано и документировано.
