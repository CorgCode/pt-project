# Исследование методов построения векторного представления хоста по сетевым взаимодействиям

## 1. Постановка задачи

### Исходная проблема

В корпоративной сети наблюдаются события сетевого взаимодействия между
хостами. Для каждого события доступны характеристики соединения:
источник и назначение, протокол, порты, длительность, количество пакетов
и объём переданных данных.

При этом заранее неизвестны роли хостов: например, является ли компьютер
рабочей станцией, сервером, сетевым сервисом или другим типом узла.

Цель проекта --- построить **векторное представление (embedding) каждого
хоста**, отражающее его сетевое поведение, а затем использовать эти
представления для:

-   поиска хостов с похожим поведением;
-   группировки хостов без заранее заданных меток;
-   анализа полученных групп;
-   обнаружения изменений поведения и переходов хостов между группами;
-   визуализации результатов и объяснения, почему два хоста считаются
    похожими.

### Основная гипотеза

Если два хоста имеют сходный характер сетевых взаимодействий, то при
правильно выбранном способе обучения их представления в векторном
пространстве должны оказаться близкими.

При этом понятие «сходный характер взаимодействий» необходимо определить
отдельно. Возможны разные варианты:

-   сходство непосредственного сетевого окружения;
-   сходство структурной роли в графе;
-   сходство используемых портов и протоколов;
-   сходство направлений и интенсивности трафика;
-   сходство временных профилей;
-   комбинация нескольких перечисленных характеристик.

Поэтому близость двух embedding сама по себе не доказывает, что хосты
имеют одинаковую реальную роль. Она означает, что они близки
относительно информации, которую конкретный метод обучения старается
сохранить.

## 2. Представление сетевых взаимодействий в виде графа

Сетевые логи естественно представить как граф.

Пусть:

-   `V` --- множество хостов;
-   `E` --- множество сетевых взаимодействий;
-   каждое ребро соответствует наблюдаемому взаимодействию между двумя
    хостами.

В простейшем случае:

``` text
A → B
B → C
A → C
```

можно представить ориентированным графом.

Однако для реального сетевого лога простого невзвешенного графа
недостаточно. Одно взаимодействие содержит дополнительные
характеристики:

-   время;
-   длительность;
-   протокол;
-   source port;
-   destination port;
-   количество пакетов;
-   количество байт.

Следовательно, исходные данные можно рассматривать как **взвешенный,
атрибутированный и временной граф**.

Это важно для выбора модели: разные методы используют разную часть этой
информации.

## 3. Данные: LANL Unified Host and Network Dataset

Для проекта выбран **LANL Unified Host and Network Dataset**.

Официальная документация Los Alamos National Laboratory указывает, что
набор содержит подмножество сетевых и host-событий из корпоративной сети
LANL примерно за 90 дней. Данные обезличены, при этом идентификаторы
хостов согласованы между сетевыми и host-событиями. Сетевые события
представлены отдельными дневными файлами.

Сетевой файл содержит следующие поля:

  Поле           Значение
  -------------- ---------------------------------------------
  `Time`         время начала события, epoch time
  `Duration`     длительность события в секундах
  `SrcDevice`    устройство-инициатор
  `DstDevice`    устройство-получатель
  `Protocol`     номер протокола
  `SrcPort`      порт источника
  `DstPort`      порт назначения
  `SrcPackets`   количество отправленных source-пакетов
  `DstPackets`   количество отправленных destination-пакетов
  `SrcBytes`     количество отправленных source-байт
  `DstBytes`     количество отправленных destination-байт

Важно не смешивать Unified Host and Network Dataset с другими наборами
LANL. Например, Comprehensive, Multi-Source Cyber-Security Events ---
отдельный набор данных.

## 4. Что такое embedding хоста

Для каждого хоста `v` требуется получить вектор:

``` text
z_v ∈ R^d
```

После обучения хосты можно сравнивать по их векторам, например с помощью
cosine similarity или расстояния.

Однако смысл этой близости определяется методом обучения.

Главный научный вопрос проекта:

> **Что именно должна означать близость двух хостов в embedding space?**

Если метод обучается на сетевых соседствах, близость может отражать
сходство соседей.

Если метод ориентирован на структурную идентичность, близость может
отражать сходство структуры вокруг узлов даже при разных конкретных
соседях.

Если в модель включены признаки трафика и времени, близость может
отражать сходство поведения.

## 5. Исследование методов

### DeepWalk

DeepWalk --- базовый подход к обучению представлений узлов графа.

Идея:

1.  из графа выполняются случайные обходы;
2.  каждый обход рассматривается как последовательность узлов;
3.  последовательности обрабатываются аналогично предложениям в задачах
    обработки текста;
4.  применяется идея word2vec/Skip-gram для получения векторов узлов.

Для проекта DeepWalk представляет интерес как baseline, позволяющий
проверить гипотезу, что информация о локальном сетевом окружении уже
позволяет получить полезное представление хоста.

### node2vec

node2vec развивает идею random-walk embedding и позволяет управлять
характером обхода графа.

Авторы формулируют задачу как обучение низкоразмерных представлений,
сохраняющих определённое понятие сетевого окружения узла. Для этого
используется biased random walk.

node2vec является важным baseline для проекта, но близость его embedding
не следует автоматически интерпретировать как одинаковую функциональную
роль хостов.

### struc2vec

struc2vec специально ориентирован на **structural identity** ---
структурное сходство узлов.

Например, два хоста могут иметь разные конкретные соседей, но сходную
структуру окружения. В этом случае структурно ориентированный метод
может считать их похожими.

Это особенно важно для задачи, где реальные роли хостов неизвестны и
могут проявляться через структуру взаимодействий.

### GraphSAGE

GraphSAGE --- подход к индуктивному обучению представлений графовых
узлов.

Вместо отдельного фиксированного вектора для каждого известного узла
модель учит функцию, которая агрегирует информацию из локального
окружения узла. Это позволяет работать с ранее не виденными узлами при
наличии необходимых признаков.

Для проекта GraphSAGE интересен в случае использования признаков
хоста/окружения:

-   распределения портов;
-   объёма трафика;
-   количества соединений;
-   временных характеристик;
-   статистик соседей.

### Временные и динамические методы

Сетевой граф в проекте не является статичным:

``` text
Day 1 → G1
Day 2 → G2
Day 3 → G3
...
```

Поэтому отдельное направление исследования --- dynamic/temporal graph
representation learning.

Это необходимо для задач:

-   обнаружения изменений поведения;
-   поиска устойчивых групп;
-   анализа cluster drift;
-   выявления резких изменений сетевого профиля.

При этом простое переобучение embedding каждый день не решает задачу
автоматически: независимые обучения могут давать разные координатные
системы. Поэтому абсолютные координаты embedding между независимыми
запусками нельзя безоговорочно сравнивать.

## 6. Кластеризация и визуализация

После получения embedding можно применить алгоритмы кластеризации.

``` text
Network logs
      ↓
Graph construction
      ↓
Node embedding
      ↓
Vector space
      ↓
HDBSCAN
      ↓
Host groups
```

### HDBSCAN

HDBSCAN может использоваться для поиска плотных групп в embedding space
и не требует заранее задавать точное количество кластеров.

Полученный кластер нельзя автоматически назвать «группой серверов» или
«группой рабочих станций». Необходимо отдельно исследовать
характеристики узлов внутри кластера:

-   распределение портов;
-   количество соседей;
-   входящий/исходящий трафик;
-   объём байтов;
-   временная активность;
-   стабильность принадлежности к кластеру.

### UMAP

UMAP целесообразно рассматривать прежде всего как средство
визуализации/снижения размерности уже полученного представления.

Важно не смешивать метод обучения node embedding и двумерную
визуализацию embedding.

## 7. Что такое «похожий хост»

В проекте понятие similarity неоднозначно.

### H1 --- сходство сетевого окружения

Хосты похожи, если они взаимодействуют с похожими узлами.

### H2 --- структурное сходство

Хосты похожи, если занимают сходную позицию/роль в структуре графа, даже
если конкретные соседи различаются.

### H3 --- поведенческое сходство

Хосты похожи, если имеют сходные:

-   порты;
-   протоколы;
-   направления;
-   объёмы;
-   частоты соединений.

### H4 --- временное сходство

Хосты похожи, если их сетевое поведение развивается похожим образом во
времени.

### H5 --- комбинированное сходство

Embedding должен учитывать несколько типов информации одновременно.

Эти гипотезы не эквивалентны. Разные методы могут оптимизировать разные
варианты similarity.

## 8. Оценка качества без известных ролей

Главная сложность проекта --- отсутствие ground-truth labels.

Нельзя просто проверить `predicted_role == true_role`, поскольку
true_role неизвестен.

### Качество кластеризации

Можно исследовать:

-   Silhouette Score;
-   Davies--Bouldin Index;
-   устойчивость кластеров при изменении параметров и выборки.

Эти метрики оценивают свойства геометрии кластеров, но сами по себе не
доказывают соответствие реальным ролям.

### Link prediction

Если embedding сохраняет полезную информацию о структуре сети, его можно
проверить на способности предсказывать скрытые связи.

### Stability

Можно повторять обучение при изменении:

-   random seed;
-   временного периода;
-   части событий;
-   параметров модели.

### Интерпретируемость

Для каждого кластера можно анализировать:

-   характерные порты;
-   направления соединений;
-   объём трафика;
-   число и типы соседей;
-   временной профиль.

## 9. Аномалии и изменения поведения

Пример изменения поведения:

``` text
Первые дни:
A → B, C, D

Позднее:
A → B, C, D, X, Y, Z
```

Возможные признаки изменения:

-   появились новые соседи;
-   появились новые порты;
-   изменилась интенсивность трафика;
-   изменилось направление взаимодействий;
-   изменился временной профиль;
-   хост перешёл в другую поведенческую группу.

Нужно различать реальное изменение поведения и изменение координат
embedding из-за переобучения модели.

## 10. Предварительный экспериментальный план

### Этап 1. Исследование данных

1.  Загрузить несколько дневных файлов.
2.  Проверить структуру CSV.
3.  Проверить пропуски и аномальные значения.
4.  Определить число уникальных хостов.
5.  Определить количество событий по дням.
6.  Найти наиболее часто используемые порты.
7.  Исследовать распределение объёма трафика.
8.  Построить базовую статистику графа.

### Этап 2. Baseline

Построить простой граф `host → host` и применить DeepWalk/node2vec.

### Этап 3. Структурный baseline

Добавить struc2vec и сравнить результат с neighborhood-oriented
подходами.

### Этап 4. Атрибутное/индуктивное представление

Исследовать GraphSAGE или аналогичный GNN-подход с признаками
хоста/окружения.

### Этап 5. Кластеризация

Для каждого embedding:

``` text
embedding → HDBSCAN → clusters
```

Сравнить:

-   число кластеров;
-   размеры кластеров;
-   долю шумовых точек;
-   стабильность;
-   внутренние метрики;
-   интерпретируемость.

### Этап 6. Временной анализ

Разбить данные на временные окна и исследовать:

-   стабильность кластеров;
-   переходы хостов между группами;
-   появление новых профилей;
-   резкие изменения поведения.

## 11. Архитектура MVP

``` text
                LANL Network Logs
                        │
                        ▼
               Data preprocessing
                        │
                        ▼
              Temporal graph builder
                        │
                        ▼
               Embedding algorithm
             ┌──────────┼──────────┐
             ▼          ▼          ▼
          DeepWalk   node2vec   struc2vec
             │          │          │
             └──────────┼──────────┘
                        ▼
                  Host embeddings
                        │
             ┌──────────┴──────────┐
             ▼                     ▼
        Similar hosts           HDBSCAN
             │                     │
             ▼                     ▼
       Explanation             Host groups
                                   │
                                   ▼
                             Temporal drift
                                   │
                                   ▼
                              Anomalies
```

Для выбранного хоста MVP должен позволять увидеть:

1.  ближайшие хосты;
2.  similarity score;
3.  общие характеристики поведения;
4.  кластер;
5.  характеристики кластера;
6.  изменения принадлежности к группе во времени.

## 12. Риски и ограничения

-   Нет ground-truth ролей, поэтому кластеры нельзя автоматически
    интерпретировать как реальные роли.
-   Понятие similarity неоднозначно.
-   Сетевой граф динамичен.
-   Разные embedding-модели кодируют разные свойства графа.
-   Большой объём событий требует внимания к памяти и вычислительной
    сложности.
-   Высокий clustering score не доказывает семантическую полезность
    кластера.

## 13. Вывод

Задача относится к network representation learning / graph
representation learning и сочетает:

-   node embeddings;
-   graph representation learning;
-   structural role discovery;
-   behavioral profiling;
-   temporal graph analysis;
-   unsupervised clustering;
-   anomaly/drift detection.

Ключевой исследовательский вопрос:

> **Можно ли по одним только сетевым взаимодействиям построить векторное
> представление хоста, в котором близость хостов отражает полезное
> сходство их сетевого поведения, а изменение положения хоста во времени
> позволяет обнаруживать изменения его поведения?**

Для ответа необходимо сравнить несколько подходов и определить, какой
тип информации сохраняет каждый метод и насколько эта информация полезна
для поставленных задач.

## 14. Предварительный анализ датасета

Фактические значения числа уникальных хостов, событий в день и наиболее
частых портов **не приводятся на данном этапе**, поскольку для их
вычисления необходимы фактические файлы датасета.

Не следует подставлять придуманные значения.

После загрузки датасета необходимо получить как минимум:

  Метрика                   Как вычисляется
  ------------------------- ------------------------------------------
  Число уникальных хостов   `unique(SrcDevice ∪ DstDevice)`
  Число событий             количество строк
  События по дням           группировка по дню/файлу
  Top source ports          частоты `SrcPort`
  Top destination ports     частоты `DstPort`
  Top протоколы             частоты `Protocol`
  Средний объём трафика     статистика `SrcBytes + DstBytes`
  Число рёбер               уникальные пары `(SrcDevice, DstDevice)`
  Средняя степень           статистика степеней графа
