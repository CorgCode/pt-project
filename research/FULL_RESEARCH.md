# Построение векторного представления хоста по сетевым взаимодействиям

## 1. Анализ задачи

### Что требуется сделать

Цель проекта — построить **векторное представление (embedding) хоста**, которое описывает его поведение в сети.

Идея заключается в том, что хосты с похожим назначением и сетевым поведением должны иметь близкие векторы, даже если их реальные роли заранее неизвестны.

На основе этих представлений система должна уметь:

- находить похожие хосты;
- группировать хосты в кластеры;
- отслеживать изменение поведения хоста во времени;
- обнаруживать переходы между кластерами;
- объяснять, почему два хоста считаются похожими.

Упрощённо:

```text
сетевые события
      ↓
описание поведения хоста
      ↓
вектор хоста
      ↓
похожие хосты / кластеры / изменения поведения
```

### Что такое «поведение хоста»

Из сетевых данных можно определить:

- с кем взаимодействует хост;
- сколько у него уникальных сетевых соседей;
- какие порты и протоколы он использует;
- сколько соединений создаёт;
- сколько данных отправляет и получает;
- преимущественно принимает или инициирует соединения;
- в какое время проявляет активность;
- насколько его поведение стабильно во времени.

Например, два компьютера могут обращаться к разным конкретным серверам, но использовать одинаковые сервисы, иметь похожий объём трафика и одинаковый режим активности. В таком случае их можно считать похожими по сетевому поведению.

### Главный исследовательский вопрос

Перед выбором ML-модели необходимо определить:

> **Что именно означает «два хоста похожи»?**

Можно выделить несколько вариантов похожести:

| Вид похожести | Что сравнивается |
|---|---|
| По активности | число соединений, интенсивность |
| По объёму | bytes, packets |
| По окружению | сетевые peers |
| По сервисам | ports и protocols |
| По направлению | incoming/outgoing |
| По времени | режим активности |
| По структуре сети | роль хоста в графе |

Скорее всего, итоговое представление должно учитывать несколько этих аспектов одновременно.

# 2. Данные

## LANL Unified Host and Network Dataset

Основной датасет проекта — **LANL Unified Host and Network Dataset** от Los Alamos National Laboratory.

Датасет содержит данные корпоративной сети примерно за 90 дней.

В нём существуют два основных типа событий:

- Network Events;
- Host Events.

По условиям проекта embedding должен строиться **только по сетевым данным**.

### Network Events

Сетевые события содержат:

```text
Time
Duration
SrcDevice
DstDevice
Protocol
SrcPort
DstPort
SrcPackets
DstPackets
SrcBytes
DstBytes
```

Из этих полей уже можно построить достаточно подробный профиль хоста.

Например:

**Активность**
- количество соединений;
- интенсивность взаимодействий.

**Peers**
- число уникальных соседей;
- наиболее частые соседи.

**Services**
- используемые порты;
- распределение портов.

**Protocols**
- TCP/UDP и другие протоколы.

**Направление**
- входящие взаимодействия;
- исходящие взаимодействия.

**Объём**
- отправленные/полученные bytes;
- отправленные/полученные packets.

**Время**
- активность по часам;
- изменение активности между временными окнами.

### Ограничения LANL

Данные деидентифицированы. Поэтому мы не можем просто посмотреть настоящую роль машины.

Это создаёт одну из основных сложностей проекта:

> Как проверить качество embedding, если настоящие роли хостов неизвестны?

При этом LANL содержит Host Events, идентификаторы которых согласованы с сетевыми данными. Потенциально их можно рассматривать как дополнительный источник для внешней проверки результатов, если они не используются при построении самого embedding.

# 3. Аналоги и существующие исследования

## 3.1. Host Behavior in Computer Network: One-Year Study

Tomáš Jirsík, Petr Velan.

Одна из наиболее близких к нашему проекту работ.

Авторы исследуют поведение хостов на реальных сетевых данных и рассматривают:

- характеристики поведения;
- временные профили;
- группировку хостов;
- стабильность поведения;
- изменение поведения во времени.

### Что можно взять

Главная полезная идея — сначала построить понятный **behavioral profile** хоста из сетевой статистики и исследовать его во времени.

Работа показывает, что host profiling можно строить на основе сетевого поведения без необходимости сразу использовать сложные нейронные сети.

Источник:

https://doi.org/10.1109/TNSM.2020.3036528

---

## 3.2. Behavior Analysis via Bipartite Graphs

Существуют работы, в которых сетевое поведение моделируется через двудольные графы.

Например:

```text
Host → Service
```

В нашем случае service можно определить через сочетание:

```text
(protocol, port)
```

Тогда:

```text
Host A → DNS
       → HTTPS
       → SSH

Host B → DNS
       → HTTPS
```

Даже если Host A и Host B взаимодействуют с разными конкретными серверами, использование похожих сервисов может говорить о похожей роли.

Это интересная идея для нашего проекта, потому что она позволяет искать **функционально похожие хосты**, а не только хосты с одинаковыми соседями.

Источник:

https://doi.org/10.1109/TNET.2013.2264634

---

## 3.3. node2vec

node2vec — один из классических методов построения embeddings узлов графа.

Сеть представляется как:

```text
host → host → host
```

node2vec выполняет случайные прогулки по графу и строит векторы так, чтобы узлы с похожим сетевым окружением получали похожие representations.

### Что можно взять

node2vec можно использовать как **первый graph baseline** и сравнить его с обычными статистическими признаками.

### Ограничение

node2vec в основном отражает близость узлов в конкретном графе.

Но:

> близкие узлы ≠ обязательно одинаковая функциональная роль.

Кроме того, классический node2vec неудобен для совершенно новых хостов.

Источники:

https://arxiv.org/abs/1607.00653

https://snap.stanford.edu/node2vec/

---

## 3.4. struc2vec

struc2vec пытается учитывать не столько непосредственную близость узлов, сколько их **структурную роль**.

Это интересно для нашей задачи.

Например, два сервера могут находиться в совершенно разных частях сети и не иметь общих соседей, но выполнять похожую функцию.

В таком случае обычный proximity-based embedding может считать их непохожими, а role-oriented representation — похожими.

Источник:

https://arxiv.org/abs/1704.03165

---

## 3.5. GraphSAGE

GraphSAGE — более сложный graph ML подход.

Главное отличие от node2vec заключается в том, что GraphSAGE учит функцию построения representation на основании признаков узла и его окружения.

Поэтому подход лучше подходит для сценария:

```text
появился новый хост
       ↓
посмотрели его признаки и соседей
       ↓
получили embedding
```

Это напрямую связано с требованием проекта работать с новым хостом.

Однако GraphSAGE разумнее рассматривать уже после простых baseline.

Источник:

https://arxiv.org/abs/1706.02216

# 4. Возможные подходы

Для проекта можно выделить несколько уровней сложности.

## Подход 1. Обычный behavioral profile

Для каждого хоста строится набор характеристик:

```text
connections
unique peers
unique ports
bytes sent
bytes received
packets sent
packets received
incoming/outgoing ratio
protocol distribution
temporal activity
...
```

Полученный набор чисел уже является вектором хоста.

### Плюсы

- просто;
- понятно;
- легко объяснять результат;
- подходит для нового хоста;
- хороший baseline.

### Минусы

- признаки выбираются вручную;
- может теряться структура сети.

Это наиболее логичный первый вариант.

---

## Подход 2. Host-host graph

Представляем сеть графом:

```text
Host A ─── Host B
   │
   ├────── Host C
   │
   └────── Host D
```

Узлы — хосты.

Рёбра — сетевые взаимодействия.

Можно учитывать вес ребра:

- количество соединений;
- bytes;
- packets.

После этого можно использовать node2vec или другие graph embedding methods.

---

## Подход 3. Host-service graph

Другой вариант:

```text
Host A ─── TCP/443
       ├── UDP/53
       └── TCP/22
```

Такое представление показывает не конкретных соседей, а **характер использования сети**.

Это может быть особенно полезно для поиска хостов одинакового назначения.

---

## Подход 4. Временной профиль

Embedding строится не один раз на весь период, а отдельно для временных окон:

```text
HOST-A / час 1 → vector
HOST-A / час 2 → vector
HOST-A / час 3 → vector
```

После этого можно отслеживать:

- изменение embedding;
- изменение ближайших соседей;
- смену кластера;
- резкие изменения поведения.

Размер временного окна нужно будет подобрать экспериментально.

Можно проверить:

- 15 минут;
- 1 час;
- 6 часов;
- сутки.

---

## Подход 5. Обучаемые embeddings

После baseline можно попробовать ML.

### Autoencoder

Получает большой behavioral vector и пытается сжать его в более короткое представление.

### GraphSAGE / GNN

Использует одновременно характеристики хоста и его сетевое окружение.

### Contrastive learning

Можно обучать представление так, чтобы похожие наблюдения одного хоста во времени находились близко.

Эти методы интересны, но сейчас их достаточно рассматривать как **следующий этап**, а не как начало проекта.

# 6. Оценка результата

Одна из основных проблем — отсутствие явной информации о настоящих ролях хостов.

Поэтому нельзя просто проверить:

```text
workstation → workstation
server → server
```

Нужно использовать несколько косвенных способов оценки.

## Temporal stability

Если поведение хоста практически не изменилось, его embedding тоже не должен резко изменяться.

Можно сравнивать:

```text
embedding(host, t)
        ↓
embedding(host, t + 1)
```

## Neighbour stability

Если сегодня ближайшие хосты:

```text
A → B, C, D
```

а завтра при похожем поведении:

```text
A → X, Y, Z
```

representation может быть нестабильным.

## Cluster analysis

Для каждого полученного кластера можно посмотреть:

- характерные порты;
- протоколы;
- количество peers;
- объёмы;
- направления;
- временной профиль.

После этого становится понятно, действительно ли группа имеет какой-либо смысл.

## Explainability

Система должна уметь объяснить:

> Почему HOST-A похож на HOST-B?

Например:

```text
Похожие хосты, потому что:

- используют похожие сервисы;
- имеют похожее количество peers;
- преимущественно создают исходящие соединения;
- имеют похожий TCP/UDP профиль;
- передают похожие объёмы данных;
- активны примерно в одинаковое время.
```

А при изменении поведения:

```text
HOST-A изменил профиль:

unique peers: 12 → 67
connections: 300 → 1700
night activity: 4% → 39%
new ports: +12
```

Для SOC такое объяснение полезнее, чем просто anomaly score.

# 7. Итог

На текущем этапе можно выделить несколько основных направлений построения представления хоста:

```text
LANL network events
        ↓
   поведение хоста
        ↓
 ┌──────┼───────────┐
 ↓      ↓           ↓
features graph   temporal profile
 ↓      ↓           ↓
 └──────┼───────────┘
        ↓
    host vector
        ↓
similarity / clustering / change detection
```

Самый простой вариант — обычный **behavioral profile**, состоящий из характеристик:

- peers;
- ports;
- protocols;
- direction;
- traffic volume;
- activity;
- temporal behavior.

Он хорош тем, что прост, объясним и позволяет получить представление даже для нового хоста.

Второе направление — **графовые представления**. Сеть можно представить как host-host или host-service graph и использовать методы вроде node2vec и struc2vec.

Более сложное направление — **обучаемые embeddings**: Autoencoder, GraphSAGE/GNN и contrastive learning. Их имеет смысл рассматривать как развитие более простых представлений.

Отдельной частью задачи является **время**. Для обнаружения изменения поведения embedding можно строить отдельно для каждого временного окна и анализировать изменение положения хоста, его ближайших соседей и принадлежности к кластеру.

Главный исследовательский вопрос проекта:

> **Какое представление сетевого поведения лучше всего позволяет находить функционально похожие хосты, если их настоящие роли заранее неизвестны?**

# Подготовка данных
### 1.1. Признаки хоста

Из чего и как составить вектор признака каждого узла сети. За основу взято представление описанное в [статье](https://www.usenix.org/system/files/raid20-bowman.pdf)

- **Доли портов/протоколов.** Для каждого хоста считается, какую долю его трафика составляет каждый известный сервисный порт (DNS, HTTPS, SMB и т.д.), отдельно как клиента и как сервера. Признаки без вариативности (общие для всех хосты) отбрасываются заранее — они не несут информации о различиях.
- **Графовые метрики узла.** Степень (сколько партнёров), центральность (насколько узел важен для связности всей сети), эксцентриситет (длина самой длинной цепочки коммуникаций от узла). Эти метрики особенно чувствительны к цепочкам логинов/подключений через несколько хостов подряд — типичному паттерну распространения атаки по сети.
- **Энтропия портов.** Мера разнообразия: хост с одним стабильным назначением (всегда порт 445) даёт низкую энтропию Шеннона, универсальный узел (много разных портов) — высокую.
- **Временные паттерны.** Доля активности в рабочие часы, концентрация активности в конкретном часе суток.
### 1.2. Профиль по протоколам/портам (из habr-статьи CyberLympha)

Модель признаков: для каждого хоста считается **частота использования каждого протокола/порта** относительно общего числа его потоков (число от 0 до 1). Формально:

- `host.proto = {frequency_i}` — вектор долей протоколов;
- дополнительно — доля потоков, связывающих хост с узлами определённых классов (`host.connectedWith`).

Общие для всех хостов признаки (Ethernet/IPv4/TCP) не несут информации и должны отбрасываться до обучения. Модель их всё равно проигнорирует, но это лишний шум в кластеризации. Значимыми оказываются признаки верхних уровней (порты/протоколы приложений), которые как раз меняются от роли к роли.

---

## 2. Способы сжатия признаков в вектор (embedding)

### 2.1. Признаковый подход: PCA
Стандартизация признаков + сжатие через PCA до заданной размерности.

Стандартизация приводит признаки к общему виду: среднему 0 и стандартному отклонению 1. Так числовые теряют математическое преимущество над вероятностными.
PCA (Principal Component Analysis) - метод, строящий новые оси координат, так чтобы по максимому сохранить информацию (условно, "растяжение" данных вдоль одной оси при условиях перпендикулярности предыдущим осям). По сути поворот системы координат.
При обучении необходимо один раз обучить на датасете (fit) и выделить статистические параметры (медиана, стандартное отклонение), иначе данные будут постоянно двигаться и пользы будет чрезвычайно мало. Но на новых данных оставить регулярное transform (меняет данные как раз используя те статистические).

**Плюс:** просто, быстро, детерминированно, легко разделить обучение/применение (fit на одних данных, transform на других), что критично для сравнения хостов в разные периоды времени.
**Минус:** учитывает только "что делает хост" (статистику), не учитывает "с кем он связан" (структуру сети); необходимо держать баланс между большим и малым количеством измерений.

Альтернатива этому — NMF (неотрицательное разложение): даёт более интерпретируемые компоненты ("роли" как неотрицательные комбинации признаков), но менее устойчиво к шуму, чем PCA.

### 2.2. Графовый подход: DeepWalk / случайные блуждания
Строится граф "хост — хост" по факту взаимодействия. С каждой вершины запускаются случайные блуждания (переходы к случайному соседу, несколько шагов подряд). Полученные последовательности используются для обучения модели по аналогии с word2vec (преобразует слово в векторное представление, которое модель "понимает" и может работать с ним дальше). Итог, вектор на вершину, отражающий её положение в структуре сети.

**Плюс:** ловит структурное сходство — два хоста могут быть похожи потому, что общаются с одними и теми же партнёрами, даже если их статистика (байты, порты) отличается.
**Минус:** не различает "что именно" передаётся между хостами (порты/объёмы) — только сам факт связи.
**Ключевой параметр:** глубина обзора графа (сколько шагов блуждания учитывать). Узкий обзор (2 шага) улавливает только близких соседей; широкий (5 шагов) — более общую структуру сети.

---

## 3. Поиск похожих хостов

**Базовый вариант:** k ближайших соседей по косинусному сходству векторов. Быстрый вариант, который имеет неслабую неточность.

**Более сложный вариант (link prediction):** вместо простого расстояния обучается отдельная модель, предсказывающая вероятность связи между парой хостов по их векторам (например, логистическая регрессия поверх поэлементного произведения двух embedding). Главным преимуществом может служить математическая способность характеризовать похожие узлы (чьи embedding имеют одинаково высокую вероятность схожих соседей) и выявлять аномалии (когда ребро имеет крайне низкую вероятность).

---

## 4. Объяснение похожести (explainability)

Три независимых источника объяснения:

1. Общие выделяющиеся признаки;
2. Общие сервисы/порты; 
3. Общие сетевые партнёры.

**Альтернативный, более "формальный" метод:** ошибка восстановления (reconstruction error). Признаки хоста сжимаются в очень маленькое пространство (1-3 измерения) и затем восстанавливаются обратно; то, что восстановилось плохо — по конкретным компонентам — прямо указывает, какие именно характеристики делают хост нетипичным. Метод даёт количественную, а не только описательную оценку аномальности, но менее нагляден для конечного пользователя без визуализации.

---

## 5. Кластеризация

**Вариант A — KMeans + подбор числа кластеров через silhouette.**
Перебираются разные значения k, для каждого считается метрика качества разбиения без разметки (насколько точки ближе к своим соседям по кластеру, чем к чужим), выбирается лучшее k.
**Ограничение:** KMeans предполагает кластеры примерно одинакового и **заданного** размера и сферической формы.

**Вариант B — [DBSCAN**](https://habr.com/ru/articles/581114/), либо его расширенная версия **HDBSCAN** + иерархическая кластеризация.
Не требует заранее знать число кластеров, находит группы произвольной формы, явно помечает "шумовые" точки, не подходящие ни под одну группу, вместо принудительного распределения по ближайшему кластеру. Иерархическая версия дополнительно даёт "дерево" вложенности кластеров — по нему можно измерить, насколько далеко (по числу уровней дерева) хост "перепрыгнул" при смене группы, что даёт более тонкую шкалу серьёзности перехода, чем просто факт "сменил/не сменил".

---

## 6. Оценка качества без разметки ролей

**Внутренние метрики кластеризации**.
Несколько независимых метрик качества разбиения на группы (согласованность точки со своим кластером против чужих; отношение внутригруппового разброса к межгрупповому расстоянию).

**Валидация через синтетические аномалии.** 
Описываются правила построения искусственных аномальных паттернов (например: цепочка подключений, где узел никогда не "возвращается" по тому же пути и не принимает подключения одновременно от нескольких источников). Такие паттерны перечисляются и искусственно вставляются в реальные данные. Дальше считается, какая доля внедрённых аномалий была найдена моделью (аналог полноты обнаружения) и сколько ложных срабатываний дала модель на немодифицированных данных.

---

## 7. Детекция дрейфа поведения / аномальных переходов во времени

**Основной принцип:** embedding и кластеризация обучаются один раз на всей истории данных (или на объединении нескольких периодов), а не заново на каждом временном окне. Это необходимо, чтобы "кластер номер 3" в разные дни означал одну и ту же группу поведения, иначе сравнение по времени лишено смысла.

**Два независимых сигнала аномальности, которые стоит комбинировать:**
1. **Дрейф вектора**. Насколько сильно физически сместилось положение хоста в пространстве embedding между периодами. Вероятностно считается устойчивым способом через медиану и медианное абсолютное отклонение.
2. **Редкость перехода между кластерами**. Не любая смена группы одинаково подозрительна. Оценивается эмпирическая частота: как часто вообще по всей сети происходит переход именно из этой группы именно в эту (мера "неожиданности" события; чем реже событие, тем больше сигнала оно несёт).

# Исследование проблемы и решений

## Резюме подходов к пострению embedding и кластеризации

### Представление данных

**1. Агрегирование признаков хоста**

Агрегировать сетевые и host-события в профиль хоста за временное окно.

***

**2. Последовательности событий**

Формировать временную последовательность (сетевых + хостовых) событий.

Применимые методы:

- Word2Vec-подобные модели
- RNN/LSTM/GRU
- Transformer

***

**3. Гомогенный граф (хостов)**

например:
- вершины - хосты
- ребра (наличие + атрибуты) - сетевые взаимодействия

***

**4. Гетерогенные графы и гиперграфы**

- Разные типы объектов и связей
    - например, двудольные графы (связь вершин хостов через вершины портов / протоколов)

- Гиперграфы


***

**Временной граф**

Разные графы для разных временных окон. Для большого объема данных и для анализа переходов между кластерами (изменения поведенческого профиля).

***

### Построение embedding

**GNN: GCN, GraphSAGE, GAT**

Построение embedding хоста по его признакам, соседям и взаимодействиям.

- GCN
- GraphSAGE - применим к большим графам
- GAT - выделять более важные (частые / интенсивные / объемные) связи между хостами через т.н. attention

**Edge-aware GNN**

GNN с учетом признаков ребер: протокол, порт, объем и тд.

**Heterogeneous GNN**

GNN с разными типами вершин и связей.
Потенциально позволяет привязать Host Events к Network Events.

**Graph Autoencoder**

GNN с восстановлением связей графа и свойств.

**DeepWalk / node2vec**

Проще, но ограничение на учитывание доп. признаков из Host Events.

# Исследование методов построения векторного представления хоста по сетевым взаимодействиям

## 1. Постановка задачи

### Исходная проблема

В корпоративной сети наблюдаются события сетевого взаимодействия между
хостами. Для каждого события доступны характеристики соединения:
источник и назначение, протокол, порты, длительность, количество пакетов
и объём переданных данных.

При этом заранее неизвестны роли хостов: например, является ли компьютер
рабочей станцией, сервером, сетевым сервисом или другим типом узла.

Цель проекта --- построить **векторное представление (embedding) каждого
хоста**, отражающее его сетевое поведение, а затем использовать эти
представления для:

-   поиска хостов с похожим поведением;
-   группировки хостов без заранее заданных меток;
-   анализа полученных групп;
-   обнаружения изменений поведения и переходов хостов между группами;
-   визуализации результатов и объяснения, почему два хоста считаются
    похожими.

### Основная гипотеза

Если два хоста имеют сходный характер сетевых взаимодействий, то при
правильно выбранном способе обучения их представления в векторном
пространстве должны оказаться близкими.

При этом понятие «сходный характер взаимодействий» необходимо определить
отдельно. Возможны разные варианты:

-   сходство непосредственного сетевого окружения;
-   сходство структурной роли в графе;
-   сходство используемых портов и протоколов;
-   сходство направлений и интенсивности трафика;
-   сходство временных профилей;
-   комбинация нескольких перечисленных характеристик.

Поэтому близость двух embedding сама по себе не доказывает, что хосты
имеют одинаковую реальную роль. Она означает, что они близки
относительно информации, которую конкретный метод обучения старается
сохранить.

## 2. Представление сетевых взаимодействий в виде графа

Сетевые логи естественно представить как граф.

Пусть:

-   `V` --- множество хостов;
-   `E` --- множество сетевых взаимодействий;
-   каждое ребро соответствует наблюдаемому взаимодействию между двумя
    хостами.

В простейшем случае:

``` text
A → B
B → C
A → C
```

можно представить ориентированным графом.

Однако для реального сетевого лога простого невзвешенного графа
недостаточно. Одно взаимодействие содержит дополнительные
характеристики:

-   время;
-   длительность;
-   протокол;
-   source port;
-   destination port;
-   количество пакетов;
-   количество байт.

Следовательно, исходные данные можно рассматривать как **взвешенный,
атрибутированный и временной граф**.

Это важно для выбора модели: разные методы используют разную часть этой
информации.

## 3. Данные: LANL Unified Host and Network Dataset

Для проекта выбран **LANL Unified Host and Network Dataset**.

Официальная документация Los Alamos National Laboratory указывает, что
набор содержит подмножество сетевых и host-событий из корпоративной сети
LANL примерно за 90 дней. Данные обезличены, при этом идентификаторы
хостов согласованы между сетевыми и host-событиями. Сетевые события
представлены отдельными дневными файлами.

Сетевой файл содержит следующие поля:

  Поле           Значение
  -------------- ---------------------------------------------
  `Time`         время начала события, epoch time
  `Duration`     длительность события в секундах
  `SrcDevice`    устройство-инициатор
  `DstDevice`    устройство-получатель
  `Protocol`     номер протокола
  `SrcPort`      порт источника
  `DstPort`      порт назначения
  `SrcPackets`   количество отправленных source-пакетов
  `DstPackets`   количество отправленных destination-пакетов
  `SrcBytes`     количество отправленных source-байт
  `DstBytes`     количество отправленных destination-байт

Важно не смешивать Unified Host and Network Dataset с другими наборами
LANL. Например, Comprehensive, Multi-Source Cyber-Security Events ---
отдельный набор данных.

## 4. Что такое embedding хоста

Для каждого хоста `v` требуется получить вектор:

``` text
z_v ∈ R^d
```

После обучения хосты можно сравнивать по их векторам, например с помощью
cosine similarity или расстояния.

Однако смысл этой близости определяется методом обучения.

Главный научный вопрос проекта:

> **Что именно должна означать близость двух хостов в embedding space?**

Если метод обучается на сетевых соседствах, близость может отражать
сходство соседей.

Если метод ориентирован на структурную идентичность, близость может
отражать сходство структуры вокруг узлов даже при разных конкретных
соседях.

Если в модель включены признаки трафика и времени, близость может
отражать сходство поведения.

## 5. Исследование методов

### DeepWalk

DeepWalk --- базовый подход к обучению представлений узлов графа.

Идея:

1.  из графа выполняются случайные обходы;
2.  каждый обход рассматривается как последовательность узлов;
3.  последовательности обрабатываются аналогично предложениям в задачах
    обработки текста;
4.  применяется идея word2vec/Skip-gram для получения векторов узлов.

Для проекта DeepWalk представляет интерес как baseline, позволяющий
проверить гипотезу, что информация о локальном сетевом окружении уже
позволяет получить полезное представление хоста.

### node2vec

node2vec развивает идею random-walk embedding и позволяет управлять
характером обхода графа.

Авторы формулируют задачу как обучение низкоразмерных представлений,
сохраняющих определённое понятие сетевого окружения узла. Для этого
используется biased random walk.

node2vec является важным baseline для проекта, но близость его embedding
не следует автоматически интерпретировать как одинаковую функциональную
роль хостов.

### struc2vec

struc2vec специально ориентирован на **structural identity** ---
структурное сходство узлов.

Например, два хоста могут иметь разные конкретные соседей, но сходную
структуру окружения. В этом случае структурно ориентированный метод
может считать их похожими.

Это особенно важно для задачи, где реальные роли хостов неизвестны и
могут проявляться через структуру взаимодействий.

### GraphSAGE

GraphSAGE --- подход к индуктивному обучению представлений графовых
узлов.

Вместо отдельного фиксированного вектора для каждого известного узла
модель учит функцию, которая агрегирует информацию из локального
окружения узла. Это позволяет работать с ранее не виденными узлами при
наличии необходимых признаков.

Для проекта GraphSAGE интересен в случае использования признаков
хоста/окружения:

-   распределения портов;
-   объёма трафика;
-   количества соединений;
-   временных характеристик;
-   статистик соседей.

### Временные и динамические методы

Сетевой граф в проекте не является статичным:

``` text
Day 1 → G1
Day 2 → G2
Day 3 → G3
...
```

Поэтому отдельное направление исследования --- dynamic/temporal graph
representation learning.

Это необходимо для задач:

-   обнаружения изменений поведения;
-   поиска устойчивых групп;
-   анализа cluster drift;
-   выявления резких изменений сетевого профиля.

При этом простое переобучение embedding каждый день не решает задачу
автоматически: независимые обучения могут давать разные координатные
системы. Поэтому абсолютные координаты embedding между независимыми
запусками нельзя безоговорочно сравнивать.

## 6. Кластеризация и визуализация

После получения embedding можно применить алгоритмы кластеризации.

``` text
Network logs
      ↓
Graph construction
      ↓
Node embedding
      ↓
Vector space
      ↓
HDBSCAN
      ↓
Host groups
```

### HDBSCAN

HDBSCAN может использоваться для поиска плотных групп в embedding space
и не требует заранее задавать точное количество кластеров.

Полученный кластер нельзя автоматически назвать «группой серверов» или
«группой рабочих станций». Необходимо отдельно исследовать
характеристики узлов внутри кластера:

-   распределение портов;
-   количество соседей;
-   входящий/исходящий трафик;
-   объём байтов;
-   временная активность;
-   стабильность принадлежности к кластеру.

### UMAP

UMAP целесообразно рассматривать прежде всего как средство
визуализации/снижения размерности уже полученного представления.

Важно не смешивать метод обучения node embedding и двумерную
визуализацию embedding.

## 7. Что такое «похожий хост»

В проекте понятие similarity неоднозначно.

### H1 --- сходство сетевого окружения

Хосты похожи, если они взаимодействуют с похожими узлами.

### H2 --- структурное сходство

Хосты похожи, если занимают сходную позицию/роль в структуре графа, даже
если конкретные соседи различаются.

### H3 --- поведенческое сходство

Хосты похожи, если имеют сходные:

-   порты;
-   протоколы;
-   направления;
-   объёмы;
-   частоты соединений.

### H4 --- временное сходство

Хосты похожи, если их сетевое поведение развивается похожим образом во
времени.

### H5 --- комбинированное сходство

Embedding должен учитывать несколько типов информации одновременно.

Эти гипотезы не эквивалентны. Разные методы могут оптимизировать разные
варианты similarity.

## 8. Оценка качества без известных ролей

Главная сложность проекта --- отсутствие ground-truth labels.

Нельзя просто проверить `predicted_role == true_role`, поскольку
true_role неизвестен.

### Качество кластеризации

Можно исследовать:

-   Silhouette Score;
-   Davies--Bouldin Index;
-   устойчивость кластеров при изменении параметров и выборки.

Эти метрики оценивают свойства геометрии кластеров, но сами по себе не
доказывают соответствие реальным ролям.

### Link prediction

Если embedding сохраняет полезную информацию о структуре сети, его можно
проверить на способности предсказывать скрытые связи.

### Stability

Можно повторять обучение при изменении:

-   random seed;
-   временного периода;
-   части событий;
-   параметров модели.

### Интерпретируемость

Для каждого кластера можно анализировать:

-   характерные порты;
-   направления соединений;
-   объём трафика;
-   число и типы соседей;
-   временной профиль.

## 9. Аномалии и изменения поведения

Пример изменения поведения:

``` text
Первые дни:
A → B, C, D

Позднее:
A → B, C, D, X, Y, Z
```

Возможные признаки изменения:

-   появились новые соседи;
-   появились новые порты;
-   изменилась интенсивность трафика;
-   изменилось направление взаимодействий;
-   изменился временной профиль;
-   хост перешёл в другую поведенческую группу.

Нужно различать реальное изменение поведения и изменение координат
embedding из-за переобучения модели.

## 10. Предварительный экспериментальный план

### Этап 1. Исследование данных

1.  Загрузить несколько дневных файлов.
2.  Проверить структуру CSV.
3.  Проверить пропуски и аномальные значения.
4.  Определить число уникальных хостов.
5.  Определить количество событий по дням.
6.  Найти наиболее часто используемые порты.
7.  Исследовать распределение объёма трафика.
8.  Построить базовую статистику графа.

### Этап 2. Baseline

Построить простой граф `host → host` и применить DeepWalk/node2vec.

### Этап 3. Структурный baseline

Добавить struc2vec и сравнить результат с neighborhood-oriented
подходами.

### Этап 4. Атрибутное/индуктивное представление

Исследовать GraphSAGE или аналогичный GNN-подход с признаками
хоста/окружения.

### Этап 5. Кластеризация

Для каждого embedding:

``` text
embedding → HDBSCAN → clusters
```

Сравнить:

-   число кластеров;
-   размеры кластеров;
-   долю шумовых точек;
-   стабильность;
-   внутренние метрики;
-   интерпретируемость.

### Этап 6. Временной анализ

Разбить данные на временные окна и исследовать:

-   стабильность кластеров;
-   переходы хостов между группами;
-   появление новых профилей;
-   резкие изменения поведения.

## 12. Риски и ограничения

-   Нет ground-truth ролей, поэтому кластеры нельзя автоматически
    интерпретировать как реальные роли.
-   Понятие similarity неоднозначно.
-   Сетевой граф динамичен.
-   Разные embedding-модели кодируют разные свойства графа.
-   Большой объём событий требует внимания к памяти и вычислительной
    сложности.
-   Высокий clustering score не доказывает семантическую полезность
    кластера.

Issue: [#6](https://github.com/CorgCode/pt-project/issues/6)

Research: Анализ поведения хостов в сетевом трафике без разметки

1. Обзор методов ML для задачи

Графовые методы и embedding — основной подход. Сетевой трафик естественно моделируется как граф: узлы — хосты, рёбра — сетевые потоки между ними. Обзор GNN для обнаружения вторжений показывает, что ~78% работ на сетевых данных используют графы потоков, а ~58% работ на хостовых данных — provenance-графы.

Ключевые алгоритмы для ролей хостов:

· node2vec — универсальный embedding, учитывает как структурную роль, так и сообщества. Не требует разметки, масштабируется, может работать на edge-устройствах. Подходит для построения baseline поведения и обнаружения отклонений.
· struc2vec, RolX, role2vec, LSME — специализированы на структурных ролях. Сравнительные эксперименты показали, что Struc2Vec и RolX лучше улавливают роль узла, чем role2vec, который «не изучает структурные свойства».
· GraphSAGE — индуктивный метод, позволяет эмбеддить новые хосты без переобучения (важно для динамических сетей).
· Self-supervised learning (masked autoencoder, contrastive learning) — активно применяется для сетевой безопасности: модель учится восстанавливать нормальные паттерны коммуникаций, а аномалии выявляются по высокой ошибке реконструкции. GraphIDS достигает до 99.98% PR-AUC на NetFlow-бенчмарках.

Кластеризация и снижение размерности: HDBSCAN — для поиска групп хостов с похожим поведением (устойчив к выбросам, не требует задавать число кластеров). UMAP — для визуализации и снижения размерности embedding перед кластеризацией.

Детекция аномалий и lateral movement: современные подходы используют динамические графы и индуктивное обучение. LARES — пример unsupervised-фреймворка, который моделирует нормальное поведение хостов на графе и локализует compromised-хосты, сохраняя точность при росте сети в 5 раз и работая в 10–100 раз быстрее аналогов.

2. Датасет LANL Unified Host and Network Dataset

· Период: 90 дней, включая red team активность с 57 по 82 день (ground truth для оценки аномалий).
· Состав: host events (Windows Logging Service) + netflow логи. Анонимизирован, но сущности можно связывать между собой.
· Масштаб: ~60,000 уникальных устройств, 15,000 пользовательских аккаунтов, 26,000 имён процессов.
· Аутентификация: в среднем 3.5 млн событий в день; ключевые EventID — 4624 (успешный вход) и 4625 (неудачный).
· Netflow: ~3,740 хостов, ~1.6 млн событий (в подвыборке для тестов).

Что можно посчитать сразу: количество уникальных хостов, распределение событий по дням/часам, топ портов, топ источников/назначений, доля broadcast/multicast, доля неудачных аутентификаций. Red team активность (дни 57–82) даёт естественную метку для валидации без ручной разметки.

3. Практические выводы

1. Стартовая архитектура: граф хостов → node2vec embedding → HDBSCAN/UMAP → детекция аномалий по расстоянию до центроида кластера.
2. Для ролей хостов: добавить struc2vec или RolX как второй канал признаков — они лучше улавливают структурные роли.
3. Для динамики: использовать индуктивные методы (GraphSAGE) или self-supervised подходы, чтобы не переобучать модель при появлении новых хостов.
