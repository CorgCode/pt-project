# Построение векторного представления хоста по сетевым взаимодействиям

## 1. Анализ задачи

### Что требуется сделать

Цель проекта — построить **векторное представление (embedding) хоста**, которое описывает его поведение в сети.

Идея заключается в том, что хосты с похожим назначением и сетевым поведением должны иметь близкие векторы, даже если их реальные роли заранее неизвестны.

На основе этих представлений система должна уметь:

- находить похожие хосты;
- группировать хосты в кластеры;
- отслеживать изменение поведения хоста во времени;
- обнаруживать переходы между кластерами;
- объяснять, почему два хоста считаются похожими.

Упрощённо:

```text
сетевые события
      ↓
описание поведения хоста
      ↓
вектор хоста
      ↓
похожие хосты / кластеры / изменения поведения
```

### Что такое «поведение хоста»

Из сетевых данных можно определить:

- с кем взаимодействует хост;
- сколько у него уникальных сетевых соседей;
- какие порты и протоколы он использует;
- сколько соединений создаёт;
- сколько данных отправляет и получает;
- преимущественно принимает или инициирует соединения;
- в какое время проявляет активность;
- насколько его поведение стабильно во времени.

Например, два компьютера могут обращаться к разным конкретным серверам, но использовать одинаковые сервисы, иметь похожий объём трафика и одинаковый режим активности. В таком случае их можно считать похожими по сетевому поведению.

### Главный исследовательский вопрос

Перед выбором ML-модели необходимо определить:

> **Что именно означает «два хоста похожи»?**

Можно выделить несколько вариантов похожести:

| Вид похожести | Что сравнивается |
|---|---|
| По активности | число соединений, интенсивность |
| По объёму | bytes, packets |
| По окружению | сетевые peers |
| По сервисам | ports и protocols |
| По направлению | incoming/outgoing |
| По времени | режим активности |
| По структуре сети | роль хоста в графе |

Скорее всего, итоговое представление должно учитывать несколько этих аспектов одновременно.

# 2. Данные

## LANL Unified Host and Network Dataset

Основной датасет проекта — **LANL Unified Host and Network Dataset** от Los Alamos National Laboratory.

Датасет содержит данные корпоративной сети примерно за 90 дней.

В нём существуют два основных типа событий:

- Network Events;
- Host Events.

По условиям проекта embedding должен строиться **только по сетевым данным**.

### Network Events

Сетевые события содержат:

```text
Time
Duration
SrcDevice
DstDevice
Protocol
SrcPort
DstPort
SrcPackets
DstPackets
SrcBytes
DstBytes
```

Из этих полей уже можно построить достаточно подробный профиль хоста.

Например:

**Активность**
- количество соединений;
- интенсивность взаимодействий.

**Peers**
- число уникальных соседей;
- наиболее частые соседи.

**Services**
- используемые порты;
- распределение портов.

**Protocols**
- TCP/UDP и другие протоколы.

**Направление**
- входящие взаимодействия;
- исходящие взаимодействия.

**Объём**
- отправленные/полученные bytes;
- отправленные/полученные packets.

**Время**
- активность по часам;
- изменение активности между временными окнами.

### Ограничения LANL

Данные деидентифицированы. Поэтому мы не можем просто посмотреть настоящую роль машины.

Это создаёт одну из основных сложностей проекта:

> Как проверить качество embedding, если настоящие роли хостов неизвестны?

При этом LANL содержит Host Events, идентификаторы которых согласованы с сетевыми данными. Потенциально их можно рассматривать как дополнительный источник для внешней проверки результатов, если они не используются при построении самого embedding.

# 3. Аналоги и существующие исследования

## 3.1. Host Behavior in Computer Network: One-Year Study

Tomáš Jirsík, Petr Velan.

Одна из наиболее близких к нашему проекту работ.

Авторы исследуют поведение хостов на реальных сетевых данных и рассматривают:

- характеристики поведения;
- временные профили;
- группировку хостов;
- стабильность поведения;
- изменение поведения во времени.

### Что можно взять

Главная полезная идея — сначала построить понятный **behavioral profile** хоста из сетевой статистики и исследовать его во времени.

Работа показывает, что host profiling можно строить на основе сетевого поведения без необходимости сразу использовать сложные нейронные сети.

Источник:

https://doi.org/10.1109/TNSM.2020.3036528

---

## 3.2. Behavior Analysis via Bipartite Graphs

Существуют работы, в которых сетевое поведение моделируется через двудольные графы.

Например:

```text
Host → Service
```

В нашем случае service можно определить через сочетание:

```text
(protocol, port)
```

Тогда:

```text
Host A → DNS
       → HTTPS
       → SSH

Host B → DNS
       → HTTPS
```

Даже если Host A и Host B взаимодействуют с разными конкретными серверами, использование похожих сервисов может говорить о похожей роли.

Это интересная идея для нашего проекта, потому что она позволяет искать **функционально похожие хосты**, а не только хосты с одинаковыми соседями.

Источник:

https://doi.org/10.1109/TNET.2013.2264634

---

## 3.3. node2vec

node2vec — один из классических методов построения embeddings узлов графа.

Сеть представляется как:

```text
host → host → host
```

node2vec выполняет случайные прогулки по графу и строит векторы так, чтобы узлы с похожим сетевым окружением получали похожие representations.

### Что можно взять

node2vec можно использовать как **первый graph baseline** и сравнить его с обычными статистическими признаками.

### Ограничение

node2vec в основном отражает близость узлов в конкретном графе.

Но:

> близкие узлы ≠ обязательно одинаковая функциональная роль.

Кроме того, классический node2vec неудобен для совершенно новых хостов.

Источники:

https://arxiv.org/abs/1607.00653

https://snap.stanford.edu/node2vec/

---

## 3.4. struc2vec

struc2vec пытается учитывать не столько непосредственную близость узлов, сколько их **структурную роль**.

Это интересно для нашей задачи.

Например, два сервера могут находиться в совершенно разных частях сети и не иметь общих соседей, но выполнять похожую функцию.

В таком случае обычный proximity-based embedding может считать их непохожими, а role-oriented representation — похожими.

Источник:

https://arxiv.org/abs/1704.03165

---

## 3.5. GraphSAGE

GraphSAGE — более сложный graph ML подход.

Главное отличие от node2vec заключается в том, что GraphSAGE учит функцию построения representation на основании признаков узла и его окружения.

Поэтому подход лучше подходит для сценария:

```text
появился новый хост
       ↓
посмотрели его признаки и соседей
       ↓
получили embedding
```

Это напрямую связано с требованием проекта работать с новым хостом.

Однако GraphSAGE разумнее рассматривать уже после простых baseline.

Источник:

https://arxiv.org/abs/1706.02216

# 4. Возможные подходы

Для проекта можно выделить несколько уровней сложности.

## Подход 1. Обычный behavioral profile

Для каждого хоста строится набор характеристик:

```text
connections
unique peers
unique ports
bytes sent
bytes received
packets sent
packets received
incoming/outgoing ratio
protocol distribution
temporal activity
...
```

Полученный набор чисел уже является вектором хоста.

### Плюсы

- просто;
- понятно;
- легко объяснять результат;
- подходит для нового хоста;
- хороший baseline.

### Минусы

- признаки выбираются вручную;
- может теряться структура сети.

Это наиболее логичный первый вариант.

---

## Подход 2. Host-host graph

Представляем сеть графом:

```text
Host A ─── Host B
   │
   ├────── Host C
   │
   └────── Host D
```

Узлы — хосты.

Рёбра — сетевые взаимодействия.

Можно учитывать вес ребра:

- количество соединений;
- bytes;
- packets.

После этого можно использовать node2vec или другие graph embedding methods.

---

## Подход 3. Host-service graph

Другой вариант:

```text
Host A ─── TCP/443
       ├── UDP/53
       └── TCP/22
```

Такое представление показывает не конкретных соседей, а **характер использования сети**.

Это может быть особенно полезно для поиска хостов одинакового назначения.

---

## Подход 4. Временной профиль

Embedding строится не один раз на весь период, а отдельно для временных окон:

```text
HOST-A / час 1 → vector
HOST-A / час 2 → vector
HOST-A / час 3 → vector
```

После этого можно отслеживать:

- изменение embedding;
- изменение ближайших соседей;
- смену кластера;
- резкие изменения поведения.

Размер временного окна нужно будет подобрать экспериментально.

Можно проверить:

- 15 минут;
- 1 час;
- 6 часов;
- сутки.

---

## Подход 5. Обучаемые embeddings

После baseline можно попробовать ML.

### Autoencoder

Получает большой behavioral vector и пытается сжать его в более короткое представление.

### GraphSAGE / GNN

Использует одновременно характеристики хоста и его сетевое окружение.

### Contrastive learning

Можно обучать представление так, чтобы похожие наблюдения одного хоста во времени находились близко.

Эти методы интересны, но сейчас их достаточно рассматривать как **следующий этап**, а не как начало проекта.

Большую часть инфраструктуры проекта не требуется писать самостоятельно.

| Инструмент | Для чего нужен |
|---|---|
| Zeek | получение структурированных событий из сетевого трафика |
| nfdump | работа с NetFlow/IPFIX |
| NetworkX | построение и анализ графов |
| scikit-learn | clustering, preprocessing, similarity, metrics |
| node2vec | простой graph embedding |
| PyTorch Geometric | GNN и более сложный graph ML |
| FAISS | быстрый поиск ближайших embeddings |

| Streamlit | простой интерфейс MVP |

### Zeek

https://zeek.org/

Может преобразовывать PCAP или live traffic в структурированные network logs.

Для LANL он не требуется, потому что LANL уже предоставляет подготовленные network events.

Но в будущем Zeek позволит применить нашу систему к реальному сетевому трафику.

### nfdump

https://github.com/phaag/nfdump

Инструменты для работы с NetFlow/IPFIX/sFlow.

Полезно изучить как пример того, откуда подобная система могла бы получать данные в реальной инфраструктуре.

### NetworkX

https://networkx.org/

Подходит для первых экспериментов с host-host и host-service graphs.

### scikit-learn

https://scikit-learn.org/

Покрывает практически весь первый baseline:

- preprocessing;
- similarity;
- K-means;
- DBSCAN/HDBSCAN;
- PCA;
- evaluation metrics.

### FAISS

https://github.com/facebookresearch/faiss

Позволяет быстро искать ближайшие векторы.

То есть:

```text
new host embedding
        ↓
      FAISS
        ↓
10 наиболее похожих хостов
```

Для первого маленького прототипа необязателен, но соответствует будущей задаче сервиса.

# 6. Оценка результата

Одна из основных проблем — отсутствие явной информации о настоящих ролях хостов.

Поэтому нельзя просто проверить:

```text
workstation → workstation
server → server
```

Нужно использовать несколько косвенных способов оценки.

## Temporal stability

Если поведение хоста практически не изменилось, его embedding тоже не должен резко изменяться.

Можно сравнивать:

```text
embedding(host, t)
        ↓
embedding(host, t + 1)
```

## Neighbour stability

Если сегодня ближайшие хосты:

```text
A → B, C, D
```

а завтра при похожем поведении:

```text
A → X, Y, Z
```

representation может быть нестабильным.

## Cluster analysis

Для каждого полученного кластера можно посмотреть:

- характерные порты;
- протоколы;
- количество peers;
- объёмы;
- направления;
- временной профиль.

После этого становится понятно, действительно ли группа имеет какой-либо смысл.

## Explainability

Система должна уметь объяснить:

> Почему HOST-A похож на HOST-B?

Например:

```text
Похожие хосты, потому что:

- используют похожие сервисы;
- имеют похожее количество peers;
- преимущественно создают исходящие соединения;
- имеют похожий TCP/UDP профиль;
- передают похожие объёмы данных;
- активны примерно в одинаковое время.
```

А при изменении поведения:

```text
HOST-A изменил профиль:

unique peers: 12 → 67
connections: 300 → 1700
night activity: 4% → 39%
new ports: +12
```

Для SOC такое объяснение полезнее, чем просто anomaly score.

# 7. Итог

На текущем этапе можно выделить несколько основных направлений построения представления хоста:

```text
LANL network events
        ↓
   поведение хоста
        ↓
 ┌──────┼───────────┐
 ↓      ↓           ↓
features graph   temporal profile
 ↓      ↓           ↓
 └──────┼───────────┘
        ↓
    host vector
        ↓
similarity / clustering / change detection
```

Самый простой вариант — обычный **behavioral profile**, состоящий из характеристик:

- peers;
- ports;
- protocols;
- direction;
- traffic volume;
- activity;
- temporal behavior.

Он хорош тем, что прост, объясним и позволяет получить представление даже для нового хоста.

Второе направление — **графовые представления**. Сеть можно представить как host-host или host-service graph и использовать методы вроде node2vec и struc2vec.

Более сложное направление — **обучаемые embeddings**: Autoencoder, GraphSAGE/GNN и contrastive learning. Их имеет смысл рассматривать как развитие более простых представлений.

Отдельной частью задачи является **время**. Для обнаружения изменения поведения embedding можно строить отдельно для каждого временного окна и анализировать изменение положения хоста, его ближайших соседей и принадлежности к кластеру.

Главный исследовательский вопрос проекта:

> **Какое представление сетевого поведения лучше всего позволяет находить функционально похожие хосты, если их настоящие роли заранее неизвестны?**
