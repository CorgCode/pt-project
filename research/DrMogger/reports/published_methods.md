# temporal_stable_hybrid

## Кратко

**Score на test дней 14–16 — 53,0** (дни 14 / 15 / 16: 52,2 / 54,7 / 52,1). Применён checkpoint дня 02 без переобучения и подбора, test дней 14–16 нигде не использовался.

Прежний протокол (test дней 02–04 просматривался при диагностике): 53,23.

Линейный гибрид поведения, собеседников и сервисов с проекцией, устойчивой между временными срезами. Прежние score по дням 02 / 03 / 04: 54,40 / 54,26 / 51,01. Модель обучена только на train дня 02; её можно применить к новым test-окнам без переобучения.

## Архитектура

Поведенческий профиль и направленные TF-IDF-профили собеседников и сервисов (SVD до 128 координат каждый) дополняются устойчивой проекцией до 128 координат. Проекция минимизирует изменение представления одного хоста между четырьмя срезами train при ограничении общей ковариации. Блоки нормируются по train и склеиваются с весами; итог — 441 координата. [Код](https://github.com/CorgCode/pt-project/blob/70347a3/scoreboard/submissions/temporal_stable_hybrid/../../temporal_stable_hybrid.py).

## Данные

Поля src, dst, dst_port, proto, bytes, packets, ts; duration участвует в подготовке окон. Используются общие когорта (6453 хоста), окна и эталоны scoreboard. Словари, IDF, SVD, масштабы и проекция фиксируются на train дня 02. Дни 03 и 04 используются только для оценки; все окна имеют общие координаты.

## Обучение и подбор

Четыре среза train; пары взвешиваются корнем из числа потоков, минимум 5 потоков в срезе, регуляризация 0,1. На validation дня 02 проверяются веса поведения {2, 3} и проекции {0, 0,5, 1, 2}. Выбраны веса 2 / 2: validation score 49,40 против 48,50 без проекции. Вся сетка сохранена в [params.json](https://github.com/CorgCode/pt-project/blob/70347a3/scoreboard/submissions/temporal_stable_hybrid/params.json). Для воспроизведения:

```bash
PT_COMPACT=1 PT_DATA=data/scoreboard_exact/processed \
  OPENBLAS_NUM_THREADS=2 OMP_NUM_THREADS=2 python scoreboard/temporal_stable_hybrid.py \
  --tune --output runs/temporal_stable_repro
python -m evaluation.submit scoreboard/submissions/temporal_stable_hybrid
```

Первая команда обучает модель и записывает новые векторы в runs; вторая оценивает приложенную посылку. Посылка содержит train и три test-файла, AUTHOR и SHARED_COORDINATES.

### Готовая модель для новых окон

[Checkpoint, параметры и SHA-256](https://github.com/CorgCode/pt-project/releases/tag/temporal-stable-hybrid-day02-v1) передаются отдельными артефактами; веса не включены в историю Git. NPZ содержит числовые параметры и словари, загружается с `allow_pickle=False`. Обучение сохранено прежним: train дня 02 [126000, 129600), validation дня 02; при применении checkpoint параметры не подбираются.

```bash
gh release download temporal-stable-hybrid-day02-v1 --repo CorgCode/pt-project \
  --pattern '*.npz' --dir runs/checkpoint
PT_COMPACT=1 PT_DATA=/path/to/current/processed python scoreboard/temporal_stable_hybrid.py \
  --checkpoint runs/checkpoint/temporal_stable_hybrid_day02.npz --output runs/stable_current
```

Владелец полной подготовки дней 14–16 может выполнить эту команду без переобучения. Выходные CSV строятся по окнам её манифеста. Для нового score нужны эти test-потоки и общие эталоны; старые test-векторы дней 02–04 их не заменяют. Score дней 14–16 в таблице получен этой командой. CI-изменение вынесено в #149.

## Ограничения

Устойчивость может подавить полезные изменения, а редкие хосты имеют шумные признаки. Test просматривался при диагностике порядка поведенческих признаков; после исправления модель переобучена с прежней validation-сеткой. Это касается только прежнего протокола. Проверяется совпадение train-векторов до и после загрузки модели.


# future_profile_predictor

## Кратко

**Score на test дней 14–16 — 52,0** (дни 14 / 15 / 16: 50,1 / 52,8 / 52,9). Validation выбрал вес нейросети 2: 51,98 против 44,85 у контроля без неё. temporal_encoder на тех же днях — 56,5 (−4,5 пункта).

Нейросеть учится предсказывать профиль хоста в следующем срезе train. Её скрытый вектор дополняет поведение, собеседников и сервисы.

Прежний протокол (test 02–04): score 56,35; дни 02 / 03 / 04: 60,43 / 55,95 / 52,68. Validation выбрал вес нейросети 2: 56,77 против 48,46 у контроля без неё. Все четыре группы метрик рассчитаны с 200 bootstrap-повторениями.

Главный контроль на том же прежнем протоколе — temporal_encoder: 63,5 против 56,35 у этой модели (−7,15 пункта). Переиспользуются его энкодер и признаки, меняется objective; дополнительно различаются веса блоков и нормировка. Поэтому эксперимент не изолирует эффект одного objective. Вес 0 проверяет только полезность новой части внутри нашего гибрида, а не преимущество над temporal_encoder.

## Архитектура

Входные признаки и MLP-энкодер заимствованы из temporal_encoder: поведение, TF-IDF/SVD собеседников, сервисов, сочетаний «собеседник + сервис», сервисы соседей и активность. Из 128 координат декодер предсказывает признаки следующего среза; добавлен контрастивный loss с весом 0,2. При построении эмбеддинга декодер удаляется, скрытый вектор склеивается с поведением и TF-IDF-блоками, затем применяется train-PCA до 384 координат. Это новый objective, исходный temporal_encoder не обучается прогнозировать будущий профиль.

## Данные

Общая train-когорта и окна scoreboard. Используются src, dst, proto, dst_port, bytes, packets, resp_bytes, resp_packets, duration, ts. Все преобразования обучаются только на train дня 02; validation дня 02 выбирает вес нейросетевого блока. Дни 03 и 04 используются только для test. Одна модель и порядок признаков для всех окон.

## Обучение и подбор

Четыре среза train, только последовательные пары «срез → следующий срез». 20 эпох AdamW, seed 17, batch 256; loss = SmoothL1 будущего профиля + 0,2 × InfoNCE. Вес нейросетевого блока выбирается из {0; 0,5; 1; 2} по полной validation-оценке. Нулевой вес — контроль гипотезы. Параметры и кривая loss сохранены в params.json.

```bash
PT_COMPACT=1 OPENBLAS_NUM_THREADS=2 OMP_NUM_THREADS=2 python scoreboard/future_profile_predictor.py --data /path/to/common/processed --tune --output runs/future_profile_repro
python -m evaluation.submit scoreboard/submissions/future_profile_predictor
```

Для обучения нужен torch; для оценки приложенных CSV он не требуется. Общая система координат обозначена SHARED_COORDINATES.

## Ограничения

В одном train-часе мало временных переходов. Предсказание может усреднять нестабильное поведение. Выбран вес 2: новая часть улучшила validation относительно нулевого веса, но на test уступила temporal_encoder. Все выводы относятся к фиксированным известным окнам benchmark; test не используется при подборе.


# relation_graph_hybrid

## Кратко

**Score на test дней 14–16 — 51,2** (дни 14 / 15 / 16: 49,6 / 51,4 / 52,5). Validation выбрал вес графового блока 2: 47,17 против 44,85 у контроля без него.

Линейный графовый гибрид описывает окружение хоста отдельно по направлению и сервису связи, дополняя его собственные признаки.

Прежний протокол (test 02–04): score 54,41; дни 02 / 03 / 04: 54,77 / 54,67 / 53,79. Validation выбрал вес графового блока 2: 51,68 против 48,46 у контроля без него. Все четыре группы метрик рассчитаны с 200 bootstrap-повторениями.

## Архитектура

Поведение и TF-IDF/SVD собеседников и сервисов заимствованы из temporal_encoder. Графы строятся отдельно для четырёх наиболее частых на train сервисов «proto/dst_port» и остальных сервисов. Для каждого типа исходящие и входящие связи независимо агрегируют SVD-профиль сервисов соседей. Ещё два блока описывают соседей через общих партнёров. Веса рёбер log1p числа потоков, влияние хабов уменьшается. Блоки склеиваются с поведением и TF-IDF, затем train-PCA сжимает результат до 384 координат. CCA и нейросеть не используются.

## Данные

Общие когорта, train, validation и три test-окна scoreboard. Используются src, dst, proto, dst_port, bytes, packets, resp_bytes, resp_packets, duration, ts. Словари, TF-IDF/SVD, список типов связей и PCA фиксируются на train дня 02. В каждом следующем окне граф строится по потокам этого окна с теми же типами и преобразованиями.

## Обучение и подбор

Четыре типа сервиса выбираются по суммарному числу потоков на train. Вес графового блока выбирается из {0; 0,5; 1; 2} по validation дня 02 с учётом всех четырёх задач; 0 — контроль. Параметры и сетка сохраняются в params.json. Дни 03 и 04 используются только при итоговой оценке.

```bash
PT_COMPACT=1 OPENBLAS_NUM_THREADS=2 OMP_NUM_THREADS=2 python scoreboard/relation_graph_hybrid.py --data /path/to/common/processed --tune --output runs/relation_graph_repro
python -m evaluation.submit scoreboard/submissions/relation_graph_hybrid
```

Все окна используют одну систему координат; посылка содержит train и три test-эмбеддинга.

## Ограничения

Популярность сервиса не задаёт реальную роль хоста. Выбран вес 2: графовый блок улучшил validation относительно нулевого веса, но может ухудшать поведенческое соседство. Результаты относятся к известным окнам benchmark.
