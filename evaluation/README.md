# Оценка эмбеддингов хостов

Здесь всё, что отвечает на вопрос **«насколько хорош этот эмбеддинг?»**: одна команда считает все метрики,
одна таблица сравнивает методы.

```text
эмбеддинг метода ─┐
                  ├─▶ evaluation.evaluate ─▶ results/<метод>.json ─▶ evaluation.scoreboard ─▶ scoreboard.md / .csv
эталон (reference)┘
```

## Быстрый старт

```bash
# 1. проверить формат файла
python -m evaluation.validate submissions/my_method/embeddings.csv

# 2. посчитать все метрики (эталон один раз строит python -m pipeline.reference)
python -m evaluation.evaluate --embeddings submissions/my_method/embeddings.csv \
    --reference-dir data/reference/test --method my_method --output results/test/my_method.json

# 3. свести все методы в одну таблицу
python -m evaluation.scoreboard --results-dir results/test --output results/scoreboard_test
```

Обычно руками это делать не нужно: `python -m experiments.end_to_end` прогоняет всё сразу —
данные, эталоны, все методы, оценку, таблицу и отчёт (см. [`experiments/README.md`](../experiments/README.md)).

## Что подаётся на вход

**Эмбеддинг** — CSV, строка на хост:

```csv
host_id,emb_0,emb_1,emb_2
Comp001,0.12,-0.31,0.04
Comp002,0.06,0.25,0.81
```

- `host_id` — непустая уникальная **строка** (`001` и `1` — разные хосты); строки сопоставляются по `host_id`, порядок не важен;
- `emb_*` — конечные числа; размерность у разных методов может отличаться;
- метод должен покрыть **всех** оцениваемых хостов (`eval_hosts.csv`), лишние хосты игнорируются;
- метод учится **только на train-окне**.

Для нескольких окон — по файлу на окно и манифест `method,window_id,path` (`python -m evaluation.validate --manifest …`).

**Эталон** (`data/reference/<validation|test>/`) строит `python -m pipeline.reference` один раз для всех методов —
из логов более позднего окна, **без участия эмбеддингов**:

| файл | что внутри | для каких метрик |
|---|---|---|
| `neighbors.csv` | `reference_window, host_id, neighbor_id, rank, split` — ближайшие по поведению | совпадение соседей |
| `features.csv` | `host_id, ref_0, …` — поведенческий профиль хоста | совпадение соседей (если нет `neighbors.csv`) |
| `edges.csv` | `host_a, host_b, source_window, target_window, label, split` — была ли связь позже | прогноз связи |
| `partners.csv` | `host_id, partner, window (source/target), count` — собеседники до и после | собеседники через похожих |
| `pairs.csv` | `host_a, host_b, label, split` — похожи ли по общим собеседникам | пары, Precision@k / Recall@k |
| `triplets.csv` | `anchor, positive, negative, split` | тройки |
| `labels.csv` | `host_id, target, split` — **только настоящие внешние метки** | линейный зонд |
| `eval_hosts.csv` | какие хосты оцениваются | все |
| `manifest.json` | окна, когорта, происхождение данных, хеши файлов | все |

Нет файла — метрика помечается «недоступна» с причиной. Файл есть, но битый — ошибка.

## Метрики

Каждая группа отвечает на свой вопрос. Это **разные** вопросы: хороший результат в одной группе
не доказывает ничего про другую.

| группа | вопрос | главное число | случайный уровень | модуль |
|---|---|---|---|---|
| Поведение | ближайшие соседи хоста в эмбеддинге — те же, что по поведению в логах? | Consistency@10 | ≈ 10/(n−1) | `knn_consistency.py`, `frozen_neighbors.py` |
| Будущие связи | по близости эмбеддингов видно, кто с кем будет общаться? | ROC-AUC связи | 0.5 | `future_links.py` |
| Будущие связи | похожие хосты подсказывают **новых** собеседников? | MRR новых собеседников | лучший бейзлайн без эмбеддинга | `partners.py` |
| Общие собеседники | похожие по общим собеседникам пары ближе непохожих? | ROC-AUC пар | 0.5 | `retrieval.py` |
| Общие собеседники | хост ближе к похожему, чем к непохожему? | точность по тройкам | 0.5 | `triplet_accuracy.py` |
| Внешние метки | внешнее свойство хоста читается из эмбеддинга? | accuracy зонда | доля самого частого класса | `linear_probe.py` |
| Узнаваемость | тот же хост через время находится по своему вектору? | Top-1, MRR, ROC-AUC пар | 1/n, 0.5 | `identity.py` (в experiments) |
| Устойчивость | удаление части связей сильно сдвигает эмбеддинг? | доля общих соседей | шум: тот же метод с другим seed | `experiments/robustness.py` |

Коротко об определениях (косинусная близость `s(x, y)`):

- **Consistency@k** — доля общих в k ближайших по эмбеддингу и k ближайших по поведению; ещё Jaccard@k и nDCG@k, k = 5, 10, 20.
- **Прогноз связи** — кандидаты: пары, у которых в целевом окне был поток (1), и случайные пары без потока (0). Ранжируем по `s`.
  Отдельно: только новые связи (которых не было в train) и обученный классификатор связей (`--fit-reference-dir`).
- **Собеседники через похожих** (идея Тихона) — для хоста A берём k = 10 ближайших по эмбеддингу, их собеседники в train
  с весом «близость × число контактов» — это прогноз собеседников A в целевом окне. MRR и Recall@10.
  Сравнивается с бейзлайнами «с кем общался раньше» и «самые популярные». Главное число — по новым собеседникам: там история бессильна.
- **Пары** — похожи: Jaccard общих собеседников ≥ τ; не похожи: Jaccard = 0; всё между — не размечено и **не** считается «непохожим».
- **Тройки** — `1{s(a,p) > s(a,n)}`, ничья — 0.5.
- **Precision@k / Recall@k** — среди размеченных кандидатов хоста, k = 1, 3, 5.
- **Линейный зонд** — логистическая регрессия на train-метках, оценка на test. Без указанного источника меток не считается.
- **Узнаваемость** — запрос: вектор хоста в окне A, галерея: все хосты в окне B. Если метод обучали на каждом окне заново,
  оси могут повернуться — тогда выравниваем поворотом (Procrustes) по половине хостов и оцениваем на другой половине.

**Интервалы.** `--bootstrap N` (по умолчанию 200) даёт 95% интервалы: хосты пересэмплируются, для пар и троек — с учётом того,
что они делят хостов. Интервалы описывают только выбор оцениваемых хостов, а не разброс по seed модели или выбору окна.

## Таблица результатов

`python -m evaluation.scoreboard` пишет:

- `scoreboard_<split>.md` — главные числа по группам с 95% интервалами, строка «случайный уровень» и средний ранг метода;
- `scoreboard_<split>.csv` — все метрики, строка на метод.

Смешивать нельзя: если методы оценены на разных эталонах, когортах, split или типах данных (синтетика / реальные),
таблица не строится, а падает с ошибкой.

## Как подключить свой метод

**Вариант 1 — просто файл.** Положите `submissions/<метод>/embeddings.csv` (эмбеддинг train-окна) и, если есть,
`validation.csv` / `test.csv` для узнаваемости во времени. Добавьте `provenance.json` вида
`{"trained_on_windows": ["train"]}`. Если все окна в одной системе координат, создайте пустой файл `SHARED_COORDINATES`.
Дальше: `python -m experiments.end_to_end … --submissions-dir submissions`.

**Вариант 2 — код в репозитории.** Новый модуль в `benchmark/methods/` с классом-наследником `GraphEmbeddingMethod`
и `METHODS = {"имя": Класс}` — он подхватится автоматически (`--methods имя`). Подробнее — [`benchmark/README.md`](../benchmark/README.md).

## Как добавить метрику

1. Напишите функцию метрики в отдельном модуле `evaluation/<имя>.py` (вход — `DataFrame` эмбеддинга с `host_id` в индексе).
2. Если нужен новый эталонный файл — постройте его в `pipeline/reference.py`, **из логов, без эмбеддингов**.
3. Добавьте запись в список `METRICS` в `evaluation/evaluate.py`:

   ```python
   Metric("my_metric", "Группа", "Короткое название", ("my_reference.csv",),
          _my_metric, "my_metric_main_number", lambda r: 0.5)   # случайный уровень
   ```

   где `_my_metric(c: Context)` пишет числа в `c.result["metrics"]`, интервалы — через `c.ci(...)`.
4. Тест рядом: `evaluation/test_<имя>.py`. Метрика сразу попадёт в результаты, отчёт и таблицу.

## Правила, без которых числа ничего не значат

- Эталон не строится из оцениваемого эмбеддинга или кластеризации по нему.
- Подбор параметров — только на `validation`; `test` — один раз для итоговых чисел.
- Числа с разных эталонов, когорт и split не сравниваются (таблица этого не допустит).
- Синтетика — проверка кода, а не результат на LANL.
- Соседи по логам и общие собеседники — **приближение** похожести, а не правда о ролях хостов. Про роли говорит только
  линейный зонд, и только с настоящими внешними метками. Придумывать метки (в том числе через LLM) нельзя.
- Бейзлайны, построенные из тех же признаков, что и эталон, совпадают с ним отчасти по построению — это точки калибровки,
  а не независимое доказательство (подробно — [`docs/METHODOLOGY.md`](../docs/METHODOLOGY.md)).
