# Поиск прироста за счёт обучения между днями

Цель пользователя: прирост не меньше 10 пунктов; желательный результат — 80+.
Достижение цели проверяется по отложенным данным, а не обещается до обучения.

при приросте минимум1 пункт на validation. При меньшем приросте эксперимент

## Протокол первого этапа

- Когорта фиксируется по исходному часу дня 02: 6453 хоста.
- Обучение: часы 11:00–12:00 дней 02 и 03.
- Подбор: день 04, 12:30–13:30. Это development/validation, его числа не являются финальным результатом.
- Новый отложенный день: 05, 12:30–13:30. Он не участвует в выборе архитектуры, эпох и весов.
- Контроль: исходный `temporal_encoder` с обучением на одном часе дня 02.
- Сравнение — на общих хостах и одних эталонах. Многодневные результаты не добавляются в исходную таблицу с другим train-протоколом.
- В этой реализации модель получает трафик нового окна. Идентификатор запрашиваемого хоста не используется для возврата сохранённого вектора по ID.

Все обучаемые преобразования оцениваются по обучающим окнам. Функция `check_chronology`
отклоняет пересечение обучающих интервалов и заход обучения в validation.
Потоки, пересекающие границы получасовых срезов, исключаются.

## Модели

`multiday_gain.py`: общие TF-IDF/SVD-словари, средний поведенческий профиль,
CCA, междневный контрастный энкодер и классификатор хостов по трафику.
Трафик каждого часа читается отдельно; агрегированные признаки остаются в памяти.

`multiday_posterior.py`: классификатор дополнен вероятностями классов.
Они строятся по признакам трафика, затем отображаются в фиксированные случайные координаты.
На validation выбирается вес этого блока. Прототипы классов обучаются только по train.
Этот вариант рассчитан на фиксированную когорту; перенос на новые хосты здесь не проверяется.

`multiday_dc.py`: адаптация DC-SAGE Родиона — направленные входящие/исходящие
сообщения, top-64, ослабление хабов, residual/skip, InfoNCE и асимметричный декодер
связей между днями. Отличия от спецификации: граф ограничен когортой, вход включает
компоненты temporal_encoder, выход 128 координат. Поэтому это адаптация, а не
буквальное повторение архитектуры 95→64.

`multiday_dc_core.py` перенесён из `methods/graph/_dc_sage.py`, ветка
`DrMogger/research-118-dc-sage-hybrid`, коммит
`eb0b9de79d8626a141c9d6cd51560bac1c5e70d7`.
Спецификация — `experiments/dc_sage/Instruction.md` той же ветки.

```bash

export PT_COMPACT=1 OMP_NUM_THREADS=4 OPENBLAS_NUM_THREADS=4 MKL_NUM_THREADS=4 VECLIB_MAXIMUM_THREADS=4

  --base /path/multiday/processed --extra /path/multiday2d/day03

  --base /path/multiday/processed --extra /path/multiday2d/day03

  --base /path/multiday/processed --extra /path/multiday2d/day03
```

Запускать последовательно. Контроль ресурсов между кандидатами использует
защиту ночного скрипта. Для сохранения локальных PyTorch-классов используется
cloudpickle; checkpoints доверенные и создаются локально.

`multiday_prepare.py` выделяет train/validation/test нового дня потоково, сохраняя
исходную когорту. Когорта не сужается по будущей активности. Манифест фиксирует
источник, происхождение данных и числа событий. Сырые данные, токены, веса и
векторы не коммитятся.

## Большой прогон после разрешения использовать больше данных

До просмотра новых дней зафиксирован `extended_protocol.json` на SSD:
train — часы 11:00–12:00 дней 02–07, validation — день 08 12:30–13:30,
test — день 09 12:30–13:30. Это новый протокол, отдельный от пилота и исходной таблицы.

```bash
.venv/bin/python -m experiments.multiday_extended \
  --work /Volumes/KINGSTON/PT_PROJECT_ML/multiday_gain
```

Координатор дожидается пилота и скачивания архивов, последовательно готовит
данные и сравнивает четыре семейства моделей на validation. Агрегаты окон
временно хранятся на SSD; CCA накапливает ковариации, не создавая огромную
матрицу всех пар дней. Контроль — исходный temporal_encoder на часе дня 02.

Для новых дней потолок Neighbors задаётся persistence из общего замороженного
эталона до оценки кандидатов. Формула среднего по задачам сохраняется; один
порог применяется ко всем моделям. Из-за нового протокола и отдельной калибровки
число 80 здесь нельзя выдавать за 80 в исходной таблице. Отчёт обязательно
показывает контроль и прирост на тех же данных.

`multiday_finish.py` фиксирует победителя по validation, копирует checkpoint,
сохраняет хеши модели и кода. Только затем координатор читает день 09,
строит общий эталон и проверяет выбранную модель и контроль. При повторном
запуске победитель не меняется, сохранённые итоговые оценки не пересчитываются.

Итог: `extended/final/REPORT.md`, `summary.json`, `model.pkl`,
`frozen_selection.json`. Цели 80+ и +10 отмечаются как достигнутые только по
фактическим числам. Ошибка стадии останавливает координатор с логом и кодом
завершения. Ни PR, ни отправка результатов в общую таблицу автоматически не выполняются.

По разрешению владельца Mac большой прогон использует до 6 потоков BLAS,
4 потока PyTorch (`PT_TORCH_THREADS`) и два процесса подготовки разных дней.
Перед вторым процессом учитывается резерв памяти первого. Если доступная память
опускается ниже 1.5 ГБ, второй день откладывается и подготовка продолжается
последовательно. По умолчанию старые команды temporal_encoder сохраняют 2 потока.

По дополнительному разрешению владельца `multiday_parallel.py` запускает до двух
семейств одновременно. Posterior использует общие преобразования и наблюдения train
из gain, а DC-SAGE — из roles. Выбранные PCA, головы и ранее посчитанные нейросетевые
эмбеддинги сбрасываются; головы обучаются заново. Чистые входные признаки окна
могут кэшироваться для повторной оценки. Обучение читает только `_xs` и `_train`,
а не эти кэши. Преобразования признаков не подбираются по validation.
Копия checkpoint принимается только после завершения записи и фиксируется отдельно.

Одновременно используются до 8 вычислительных потоков: новые пары получают по 4;
рядом с уже работающим шестипоточным процессом второй получает 2. Допуск второго
процесса учитывает резерв памяти; при доступной памяти ниже 2 ГБ второй останавливается,
его незавершённые артефакты сохраняются в `retries/`, а задача повторяется последовательно.
Выбор победителя и единственная финальная проверка сохраняют прежний протокол.
