# Самостоятельное обучение модели по схеме multiday_codebook_plus

`train_plus` обучает модель с нуля на подготовленных CSV. Готовые веса, внешний диск и цепочка старых исследовательских артефактов не требуются. Сырые потоки, модели и результаты остаются в `runs/`.

Это **реконструкция по опубликованной схеме**, а не исходный checkpoint лидера. Основания: карточки `scoreboard/submissions/multiday_codebook{,_plus}` на `70347a3`, функции обучения source/ранжирования в `experiments/multiday/{codebook,listwise,bigraph,bag}.py` на `86d709d`. В карточке plus прямо отмечено, что код головы и сборки не опубликован. Исходная 896-мерная основа зависела от нескольких ранее подобранных моделей; её точное воспроизведение по одной карточке невозможно. Здесь вместо этой цепочки используется явно описанный самостоятельный кодировщик. Имя локального метода — **rebuilt_plus**, опубликованные 70,04 ему не приписываются.

## Архитектура и отличия

1. Поведенческий профиль строится штатным `build_reference_features`; колонки и scaler выбираются только на source. Направленные собеседники и сервисы хешируются в 32768 столбцов, затем TF-IDF/SVD по 128 координат. Добавляется направленное распространение сервисов по соседям и через два шага. Поведение имеет вес 4, peers/services — 1, diffusion — 0,5. PCA даёт 512 координат.
2. Две MLP-головы по 128 и 256 координат обучаются узнавать хост между **обучающими** окнами: классификация известных хостов, симметричный contrastive loss и сохранение сходства исходных профилей. Собственный host_id служит меткой и группировкой, отдельным признаком не является. Склейка 512+128+256 даёт 896 чисел. Центры и масштабы блоков фиксируются по source.
3. Source-codebook 896 обучается по будущим контактам **только исторических train-окон**. Потери: listwise «любой правильный новый собеседник», KL сохранения соседства и привязка к начальному профилю. Голосование использует реальные частоты source, смесь soft-соседей 0,1 и top-10 0,9. В отличие от прежнего `codebook.py`, отдельного donor-CE с весом 0,25 здесь нет.
4. Штатный поздний адаптер — Ridge с alpha=1 и полураспадом весов дней 3. Смесь с исходным трафиковым вектором выбирается из 0/0,5/1 по **полному development-score**. Исходный алгоритм подбирал её на внутренних исторических днях; при трёх днях используем объявленный development.
5. Голова новых контактов 64 учится тем же listwise-loss, KL к соседству source имеет вес 3. Локально — 200 stochastic steps, а не опубликованные 10 полных эпох. Графовый блок — 64 собственных вектора нормированного симметричного графа с наибольшими |eigenvalue|, история с полураспадом 3 дня. Веса при склейке — 1/2/0,1. Итог — 1024 числа. Поздние дополнительные блоки получаются soft top-20 lookup исходных профилей, температура 0,02. При малой синтетической когорте размерности автоматически сокращаются.

Все эти параметры задают воспроизводимый самостоятельный baseline. Это не заявление об идентичности архитектуры/оптимизации каждого скрытого этапа лидера.

## Что сравнивает эксперимент

- Сначала фиксирует source и сравнивает штатный адаптер, новый Ridge, редкие устойчивые контакты, gate и смеси редких контактов со штатным прогнозом. **Штатный адаптер может выиграть**, при равенстве он имеет приоритет.
- Обучает teacher полезных замен только на исторических train-переходах. Низкоранговая поправка имеет варианты 0/0,1/0,2; максимум допустимой потери сырого Neighbors@10 — 5%.
- Для **каждого изменённого source заново обучает IdentityAdapter на его окончательные координаты**, включая выбор варианта на development. Простая передача прежнего Identity через lookup не считается дообучением.
- Выбирает окончательный вариант по полному development-score. Нулевой вариант остаётся допустимым. После сохранения checkpoint и frozen_selection впервые обрабатывает diagnostic test.
- Выдаёт baseline / Identity-only / neighbors-only / combined с заново обученным Identity. В этих четырёх строках используется выбранная сила поправки; если выбран ноль, соответствующие строки совпадают. Поля `candidates` сохраняют результаты ненулевых поправок на development.
- На **одних и тех же 128 запросах** отдельно считает прямой прогноз, сильные временные эвристики, исходное голосование, oracle принудительных замен и голосование выбранного итогового вектора. Oracle использует ответы исключительно для диагностики после фиксации; не обучает модель на test и не является достигаемым embedding-score. Это конструктивная нижняя оценка возможностей перебора, не доказанный максимум всех десяток.

Локальные эталоны используют одну фиксированную исходную когорту, активность >=300 в целевом окне, точные частоты source для partners, контактные множества для edges/pairs и штатный поведенческий профиль целевого окна. Потолок Neighbors отдельно рассчитывается как persistence того же source-профиля на той же целевой когорте; фиксированные ориентиры дней 14–16 не переносятся. Классификатор Links обучается на переданном более раннем probe_reference с тем же source-интервалом. Без любой из пяти обязательных метрик score не выдаётся. Неопубликованные роли хостов не предполагаются.

## Запуск и передача

Установить проектные зависимости и `torch`. Отредактировать `plus_example.json`; пути разворачиваются из переменных окружения. Файлы подготовленных данных не перезаписываются; каждая выходная папка должна быть новой.

```bash
export PT_EXPERIMENT_ROOT=/path/to/data PT_REPO_ROOT=/path/to/repository
export OPENBLAS_NUM_THREADS=2 OMP_NUM_THREADS=2 VECLIB_MAXIMUM_THREADS=2
python -m experiments.frozen_adapters.train_plus --config config.json --output runs/rebuilt_train01
python -m experiments.frozen_adapters.plus_experiment --config config.json \
  --trained runs/rebuilt_train01 --output runs/rebuilt_experiment01
python -m experiments.frozen_adapters.plus_infer \
  --checkpoint runs/rebuilt_experiment01/selected.joblib \
  --source runs/rebuilt_experiment01/source.csv --flows next.csv \
  --start START --end END --day DAY --cache runs/cache --output runs/next.csv
```

`train_plus` читает только train. `plus_experiment` сохраняет `selected.joblib`, отдельный `identity_only.joblib`, `frozen_selection.json`, source CSV, все оценки и локальные эталоны. `plus_infer` только применяет checkpoint: проверяет когорту, source-матрицу и временной cutoff, не вызывает fit. Кэш можно перенести через `--cache`; версии окружения записаны в protocol.json. Checkpoint надо передавать как доверенный локальный артефакт, как и остальные модели проекта.

Для полной истории расширить train до дня 12, поставить development13 и объявить более поздние окна. Число шагов нужно масштабировать по объёму данных; локальные значения нельзя считать подобранными для 32 часов. Исторические открытые 14–16 остаются диагностикой. Пока нет результата на полном протоколе, цели 90/95 — только численные ориентиры.

`source_window` задаёт именно канонический час дня 02, 11–12, даже если обучающая история начинается с 10:00. Он должен лежать внутри объявленного train. Ранние часы используются для обучения трафиковых признаков; исторические цели codebook берутся из последующих дней, source-контакты и начальный профиль остаются от канонического часа.
