# Матрица сходства и сопоставление графов

Самостоятельный метод из подготовленных потоков. Не загружает `multiday_codebook_plus`, `temporal_stable_hybrid` или их векторы. Source — симметричная обучаемая матрица S для фиксированной известной когорты; позднее окно — частичное совместное сопоставление с историческим графом. Название метода в локальных результатах: `similarity_graph`.

## Обучение S

Начальная матрица строится из среднего исторического поведенческого профиля и TF-IDF по историческим собеседникам, веса 0,8/0,2. Используются штатные поведенческие признаки; их колонки и scaler фиксируются на каноническом source-часе. На диагонали S — нули. Небольшой симметричный jitter 1e-5 задан до обучения для разрешения вырожденных top-k-ничьих.

Далее coordinate search пробует изменение S[i,j] и S[j,i] одновременно. Для **обоих** хостов на каждом историческом train-окне заново выбираются десять соседей, положительные веса умножаются на настоящие частоты канонического source, учитываются старые контакты, собственный узел и все конкурирующие допустимые партнёры. Цель MRR — первый из **любых** правильных новых партнёров, ничьи имеют средний ранг. Полезность кандидата зависит от остальных девяти, а не только от факта нужного контакта.

Обучающий критерий — сумма исторического MRR, нормированного сырого Neighbors@10 с весом 2 и нормированного AUC размеченных shared-partner пар. Для pair AUC поддерживаются точные изменения глобального ранга положительных/отрицательных пар, а не MSE произвольной метки. Принятые симметричные обновления строго улучшают этот критерий. **Это не точная производная полного scoreboard:** Identity и Links оцениваются позже; окончательный выбор делается по полному development-score. Доступны supporters правильных партнёров, поведенческие соседи и сильные текущие кандидаты; перебор кандидатных десяток не исчерпывающий.

`objective=score_proxy` заменяет эту первую контрольную цель на логарифм нормированных колонок с шансом, потолком и floor штатной шкалы: log(NewMRR)+2log(Behavior)+2log(Pairs). Это восемь логарифмов score при фиксированных Links и Identity. Контакты/пары пересчитываются точно, Neighbors выше потолка не получают лишнюю награду, но сырой Neighbors на каждом историческом окне защищён ограничением >=95% исходного уровня. Links и Identity всё равно требуют полной development-проверки. Для обоих критериев тестируется совпадение суммы принятых изменений с фактическим изменением глобальной цели.

`queries_per_pass` ограничивает бюджет стохастического поиска. Пример 2×96 запросов на окно — пилотная проверка, не обучение до глобального оптимума. Для полного прохода указать размер когорты. Объём S для 6453 узлов — 41,6 млн ячеек / 20,8 млн независимых внедиагональных пар; хорошее начальное значение назначено всем парам, coordinate search изменяет только выбранные.

## Точное и компактное представления

Для симметричной S вычисляется B=max_i sum_j |S[i,j]|. B >= ||S||₂. Выбирается ε=0,9/max(B,1), K=I+εS, Z=Cholesky(K). Это положительно определённая матрица с единичной диагональю; cosine(Zi,Zj)=εSij при i!=j. Сохраняются top-10, знаки весов, относительные голоса и ранги partners/pairs. Реализация проверяет максимальную ошибку Gram и нормы строк; отдельно публикует фактическое совпадение top-10/MRR до и после перехода к векторам. Для плохо разделённых численных ничьих одной формальной гарантии недостаточно.

Полный контроль имеет до 6453 координат, штатный валидатор размерность не ограничивает. Варианты 384/512/1024 инициализируются положительной спектральной частью S и обучаются воспроизводить её соседство через KL между распределениями сходства. Это **обучаемое сжатие**, на которое точная гарантия не переносится: overlap десяток и MRR измеряются заново.

Дополнительный `compact_loss=top10` учит именно найденные десять соседей, с весами от положительных S, и сохраняет плотный KL как регуляризатор с весом 0,25. Это проверка узкого места, где обычный плотный KL сохранял классы похожести, но терял конкретную десятку. Шаги можно задать через `build --compact-steps`; фактическая цель, число шагов и история сохранены отдельно для каждого кандидата. `--skip-full-rank` предназначен для последующих сравнений компактных вариантов после отдельного полного контроля; пропущенному полному варианту score не приписывается.

Дополнительный `--psd-edge-control` использует менее консервативную достаточную проверку: явно вычисляет λmin(S) и ставит ε=0,999/(-λmin), так что λmin(K)=0,001. Условие ε<1/||S||₂ достаточно, но не необходимо; при большом положительном собственном значении оно может чрезмерно подавлять весь сигнал относительно I. Контроль у границы PSD по-прежнему точно сохраняет косинусные порядки и голоса, а Cholesky и Gram проверяются численно. Его собственные результаты Identity/Links также выбираются по development; преимущество не предполагается.

Гарантия касается трёх косинусных задач, не полного score. Штатный Identity всегда делает Procrustes по половине хостов, даже при объявленной общей системе координат. При D больше числа калибровочных пар поворот в ортогональном дополнении неоднозначен: в локальном синтетическом примере N=D=60, калибровка=30, одинаковые A=B дают прямой Top-1=1, но Procrustes Top-1=0,2. Это воспроизводимый пример на текущем численном backend, не универсальная константа. Единичная диагональ K также не даёт гарантии качества Links: классификатор и его случайный ориентир зависят от размерности.

## Совместное узнавание позднего графа

Исторические профили — направленные контакты и сервисы, TF-IDF по различным хостам, устойчивость по различным дням, активность. Для каждого query берутся 30 кандидатов по максимуму сходства с историческими наблюдениями; собственный ID не подаётся признаком и не используется для бонуса диагонали.

Частичное сопоставление имеет неизвестное соответствие с неограниченной вместимостью. Реальные столбцы имеют массу <=1, строки с unknown суммируются в 1. Итерации пересчитывают совместимость A_query P A_historyᵀ только для кандидатных пар и уточняют soft assignment. Хабы ослаблены симметричной нормировкой графа. При нулевом graph_weight остаётся частичное unary-сопоставление; этот контроль участвует в выборе. Перестановка порядка query-узлов переставляет выход, а не меняет смысл кандидатов.

Опциональный `refine` при фиксированном source сравнивает soft-вывод с жёстким частичным соответствием. Последнее точно решает **линейную** sparse assignment-задачу на окончательных graph-refined вероятностях, с отдельным dummy для каждого query; это не заявление о глобальном оптимуме исходной квадратичной графовой задачи. Soft и hard выбираются только по development, затем сохраняется новый freeze до test. Исходный вариант всегда остаётся кандидатом.

Флаг `refine --joint-context` дополнительно обучает профильный банк на совместных токенах «направление × собеседник × протокол × порт», сохраняя исходный банк контролем. Они извлекаются потоково из тех же train-файлов, без собственных ID и self-flow. Для query используются только его текущие потоки; source-векторы не меняются. Публикуется recall истинного ID среди 30 кандидатов как отдельная диагностика с метками, **не вход алгоритма**. При переносе inference переопределяет путь к этому кэшу через `--cache`.

Поздний вектор — взвешенная сумма **окончательных** source-векторов и общего fallback для unknown. Нет последующей передачи старого адаптера в изменённое пространство. Метод применим к известной source-когорте; inference допускает отдельный список target-узлов, но незнакомому хосту сопоставление может быть неизвестно. Алгоритм — прозрачный итерационный baseline класса partial graph matching; это не воспроизведение обученной модели из [Ratnayaka et al., ICLR2025](https://proceedings.iclr.cc/paper_files/paper/2025/hash/cfa8440d500a6a6867157dfd4eaff66e-Abstract-Conference.html).

## Поворот под Links

После выбора лучшего неповёрнутого варианта по development отдельно учится ортогональный блок 64×64 в source-координатах, Cayley-параметризация. Исторические train-рёбра обучают вспомогательный классификатор |Za-Zb| / Za*Zb; **сам штатный Links-классификатор затем обучается заново на более раннем probe_reference**. Поворот принимается только при лучшем полном development-score. Это ограниченный поиск поворота, не оптимум всего O(6453).

Все source-косинусы сохраняются математически и проверяются численно. Улучшение Links не гарантировано. Официальный Procrustes в неполном ранге может численно выбирать другое дополнение; поэтому Identity также переоценивается, не объявляется неизменным.

## Полная проверка

Всегда нужны Behavior, learned Links, New partners, Shared partners и Identity. Используются проектные функции метрик, канонические правила кандидатов и одинаковая активная часть исходной когорты. Локальный потолок Neighbors рассчитывается по persistence на том же окне. Нельзя подставлять к нему потолок дней 14–16. Новые роли хостов не придумываются.

`references` может указывать прямо на `scoreboard/data/reference/{test,test_day15,test_day16}`. Проверяются границы окон, активная когорта, SHA CSV и совпадение source/target-контактов с потоками. Канонический потолок берётся только при точном совпадении файлов с общей таблицей. Для произвольного reference в формате `pipeline.reference` без потолка создаётся локальная копия manifest и вычисляется persistence стандартного source-профиля; исходные файлы не изменяются. В самостоятельно построенных локальных эталонах этого исследования self-flow исключены и из поведенческого профиля; это отдельная версия эталонов, не каноническая таблица.

В полной размерности одна пара признаков Links могла бы создать многогигабайтные копии endpoint-матриц. Большие train-признаки записываются порциями в временный float64 memmap и передаются **обычному sklearn LogisticRegression(C=1,max_iter=2000)**; prediction и косинусы размеченных пар считаются порциями. Малые задачи используют эквивалентные batched loss/gradient с теми же L-BFGS tolerances. Случайные векторы, StandardScaler, источники и окна не меняются. Тесты сравнивают обе реализации со штатной, включая все пять метрик и полный score. Временный memmap удаляется после fit.

## Запуск

```bash
export PT_DATA_ROOT=/path/to/data PT_ARTIFACTS=/path/to/runs PT_REPO_ROOT=/path/to/repo
export OPENBLAS_NUM_THREADS=2 OMP_NUM_THREADS=2 VECLIB_MAXIMUM_THREADS=2
# Проектные зависимости; для сжатия и обучения поворота дополнительно torch.
python -m experiments.similarity_graph.prepare --config config.json --output runs/sg_train01
python -m experiments.similarity_graph.build --trained runs/sg_train01 --output runs/sg_vectors01
# Дополнительный точный контроль: добавить --psd-edge-control.
python -m experiments.similarity_graph.run --config config.json \
  --trained runs/sg_train01 --built runs/sg_vectors01 --output runs/sg_experiment01
# Необязательное сравнение soft/hard при том же source:
python -m experiments.similarity_graph.refine --config config.json \
  --checkpoint runs/sg_experiment01/model.joblib --joint-context --output runs/sg_matching01
python -m experiments.similarity_graph.infer --checkpoint runs/sg_experiment01/model.joblib \
  --source runs/sg_experiment01/source.csv --flows late.csv --start START --end END --day DAY \
  --cache runs/cache --output runs/late.csv
```

Каждая выходная папка должна быть новой. `example.json` использует три train-часа 02/03/04 и более поздние development/test дня 04. Это отложенные часы, **не целиком отложенный день** и не новая слепая проверка. Для реального rolling-day эксперимента нужны следующие не использованные дни. Тимлид может расширить train до дня 12 и поставить development13; source_window остаётся каноническим часом 02 независимо от начала train. Открытые 14–16 — диагностика.

Сохраняются S, векторы, профильный matcher, обучение, SHA входов/весов/кода, фактические сохранения соседства, все development-кандидаты и frozen_selection **до чтения test**. Inference не обучает модель. Результаты и веса локальные; в Git только код, конфигурационный пример и документы. Схема не даёт обещания score 90/99; это проверяется экспериментом.
