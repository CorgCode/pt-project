эксперимент с явно другим бюджетом данных.

## A → B: прямая поправка Identity

`TemporalDonorIdentity` принимает поздний вектор исходного адаптера
`late_base` [Q,896] и признаки наблюдаемого трафика `late_context` [Q,64].
По умолчанию применяется линейная поправка 960→896:

```
late_new = late_base + eta * (W · [late_base; late_context] + bias)
```

Вес и bias линейного слоя обнулены: при любом конечном eta результат **точно
совпадает с исходным тензором**, без нормализации и изменения числа координат.
Необязательный `ModelConfig(correction='mlp')` включает MLP 960→128→896 с
обнулённым последним слоем; он оставлен для последующего сравнения, после
проверки линейной модели. Обучен только линейный вариант от y0; MLP не обучался.
Собственный ID query не входит в сеть; порядок строк не влияет на результат.
Source-векторы не изменяются. Это фиксирует source-based метрики при тех же
файлах и эталонах, а также не меняет размерность их случайных ориентиров.

`episodic_identity_loss` считает центрирование по калибровочным хостам,
ортогональный Procrustes поздних векторов к source и cross-entropy ранжирования
**всей evaluation-галереи**. Добавлен необязательный L2-штраф отклонения от
старого адаптера. Доступны `alignment_gradient='stop'` и `'svd'`: первый
фиксирует матрицу поворота при backprop, второй дифференцирует через SVD.
Stop-gradient приближает обучение и игнорирует влияние параметров на сам
поворот; нельзя считать его точной производной официальной процедуры.
Опциональная диагональная регуляризация численно меняет обучающий Procrustes.
Она **не является** частью официального оценщика. При повторяющихся/нулевых
сингулярных значениях SVD-градиент может быть неопределённым; 896 измерений
и около790 калибровочных хостов дня14 делают эту проблему существенной.
Настоящий выбор — по `evaluation.identity.identity_retrieval` со штатными
разбиением, обработкой ничьих и обычным SciPy Procrustes, без регуляризации.

## C: историческая геометрия доноров

`history.contact_profiles` собирает три host×partner CSR-матрицы из переданных
предподготовленных наблюдений:

1. `days`: число разных дней, в которых встречался контакт;
2. `recent`: сумма бинарных присутствий по окнам с полураспадом по дням;
3. `periodic`: сумма присутствий с гауссовым весом близости часа суток к
   заранее указанному целевому часу (ширина 2 часа, циклические сутки).

Второй и третий профили суммируются **по наблюдаемым окнам**, поэтому несколько
окон одного дня увеличивают вес; первый профиль учитывает каждый день один
раз. Окон, которые не наблюдались, нет в матрицах и они не считаются нулевым
трафиком. Принимается необязательный prefix-fitted IDF. Все наблюдения должны
заканчиваться до cutoff; словарь и IDF предоставляются вызывающим кодом и
обязаны быть обучены на том же разрешённом префиксе. Все матрицы имеют один
порядок хостов и партнёров. Готовый извлекатель из NetFlow пока не реализован.

`model.source_vectors` формирует
`[sqrt(w0)·unit(base); sqrt(w1)·unit(days); sqrt(w2)·unit(recent); sqrt(w3)·unit(periodic)]`.
Весам требуются неотрицательность и сумма1. Пустые строки блоков остаются
нулевыми; вектор не перенормируется до передачи оценщику. Для весов
`[1,0,0,0]` возвращается **точная копия исходных896 координат**, а не расширенный
вектор с нулевыми колонками — так baseline сохраняет и размерность.

`donor_grid.evaluate_grid` принимает явно переданный набор весов и вызывает
**штатный** `evaluation.partners.partner_ranking` на активных хостах: реальный
top10, cosine, raw counts, исключения и midrank. Это диагностика MRR, **не
выбор победителя по полному score**. Из-за высоких размеров разреженные блоки
уплотняются только для активных хостов; может потребоваться много памяти.
Если применяется SVD/другая проекция, её нужно обучить на prefix заранее и
подавать уже спроецированные признаки: hard MRR вычисляется после проекции.

`hard_votes`, `soft_votes`, `first_positive_rank_loss` и
`preserve_neighbors_loss` сохранены для возможных последующих исследований.
Сейчас grid не обучает donor-нейросеть. Soft-loss не является настоящим MRR,
KL не гарантирует сохранение raw Neighbors@10.

## Что ещё требуется до полноценного прогона

- Определить и реализовать обучение/преобразование `late_context` по разрешённой
  истории и формирование входных CSR-матриц с общим словарём. Есть runner первого Identity-опыта и его checkpoint; runner для контекстных признаков и расширенной модели пока отсутствует.
- Для варианта C нужен новый late-адаптер **расширенной размерности** и его
  отдельный контроль. Нельзя выдавать дополненный нулями старый вектор за
  обученный адаптер. `ModelConfig(base_dim=...)` позволяет создавать residual
  необходимой размерности, когда такой baseline будет построен.
- Rolling-prefix validation требует отдельных основ, обученных до каждого
  псевдотеста. Финальный найденный checkpoint уже видел дни02–12; проверка на
  днях внутри этой истории с ним — только внутренняя диагностика.
- Для обучения residual предпочтительны out-of-fold выходы старого адаптера на
  последующих исторических окнах, которых он и его основа не видели. В каждом
  эпизоде обучить основу, старый адаптер и признаки только на доступном
  префиксе, а на следующем окне получить сохранённые предсказания. Разделить
  временные окна обучения residual, выбора параметров и проверки качества.
- Host-disjoint оценка — дополнительная диагностика зависимости от известных
  хостов; основная проверка — будущие окна целевого протокола.
- Выбор по нескольким историческим разбиениям и дню13, затем фиксированный
  benchmark14–16. Эти дни уже изучены; новый закрытый период нужен для
  независимого подтверждения. Для каждого кандидата проверять все пять метрик,
  новый dimension-dependent Links chance и сырой Neighbors@10.

## Критерии проверки

- Identity-only: разница официального Identity Top-1 на одинаковых временных
  окнах относительно старого адаптера; source-метрики контролируются отдельно.
- Донорная геометрия: New partners MRR с настоящим top10 и контроль поведения,
  Links и Pairs. Если сравнивается полный вариант C, Identity также обязательна.
- Совместный метод: разница полного score, рассчитанного по каждому окну и
  усреднённого по протоколу. Важны повторяемость по временным разбиениям и
  оценка на ранее закрытом периоде. Host-bootstrap сам по себе не измеряет
  перенос по дням при общей галерее и общем выравнивании.
- Окна выбора весов и оценки качества разделяются. Неудачная сетка отвергает
  лишь проверенные комбинации; это не глобальный потолок достижимого MRR.

Проверка использует **только синтетические данные** и не обучает модель:

```
OPENBLAS_NUM_THREADS=2 OMP_NUM_THREADS=2 .venv/bin/python -m pytest experiments/temporal_donor_identity/test_model.py -q
```
