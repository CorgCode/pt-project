# Донорское голосование: диагностика дня13

**Сильный сигнал есть до построения эмбеддингов, но показатель 80 ещё не
получен.** На выборке384 из1323 оцениваемых хостов дня13 исходная десятка
дала MRR0,1403, поиск с правильными ответами —0,4817, а выбор по разрешённой
истории —0,3170. Это независимые для каждого хоста списки, не одно общее
пространство и не показатель общей таблицы. День13 ранее изучался.

## Протокол

Source-векторы — оригинальный multiday_codebook, обученный до12; известный
source02 задаёт словарь и частоты голосования. Окно13 12:30–13:30, активны1757,
с хотя бы одним подходящим новым партнёром1323. Случайная выборка384 без
замены, seed17. На всей когорте штатный baseline New partners MRR0,16036;
на выборке384 —0,14027 (это разные множества хостов).

Для каждого query сравнивается строго одно активное множество, фиксированный
source02, исключение собственного хоста и старых контактов, положительные
веса cosine из исходной геометрии, midrank при ничьих и лучший правильный
контакт. Прямой `evaluation.partners` воспроизводит общий baseline на всех
1323; тесты сравнивают midrank и голосование на синтетических данных.

| Вариант | Что разрешено | MRR на 384 |
|---|---|---:|
| Исходные top10 | Исходные cosine | 0,14027 |
| Поиск по истории | Контакты и активность дней03–12, fixed source02, активная когорта13 | 0,31696 |
| Bounded oracle | Истинные контакты13, fixed source02, активная когорта13 | 0,48173 |

У исторического варианта улучшилось203 запроса, ухудшилось145, без изменений36.
У oracle улучшилось329 из384, ухудшений нет. Из384 запросов383 имели хотя бы
один прогнозируемый исторический контакт; у347 top8 прогноза включали хотя бы
один правильный контакт13. Это post-hoc диагностика, не вход модели.

Историческое правило: для каждого хоста собрать встречи партнёров в днях03–12,
учесть затухание с полураспадом3 дня, удалить старые контакты source02 и
собственный ID, выбрать восемь наиболее частых оставшихся. Для каждого найти
до12 активных доноров с крупнейшими исходными count, плюс исходных top10;
при одинаковых count используется детерминированный порядок. Начав с исходной
десятки, жадно менять доноров до двух проходов. Цель — ожидаемый reciprocal
rank в *категориальном* распределении восьми предсказанных контактов; это
суррогат, а не точное ожидание first-ANY MRR. Прогноз использует только
историю до12; правильные ответы13 используются отдельно для итоговой оценки.
Активная когорта13 предоставляется как в задаче оценщика. Выбор десятки
выполнен отдельно под этот список активных хостов, что нельзя напрямую
реализовать единственным фиксированным source-вектором для всех окон.

Oracle использует действительные правильные контакты13, ищет поддержку до12
доноров на цель и делает те же жадные замены. Это ограниченный поиск с
метками; достигнутая величина является результатом алгоритма, **не верхней
границей**, не прогнозом и не оценкой честной модели. Он использует исходные
cosine-веса, но может произвольно отдельно выбирать десятки: общая
симметричная/PSD cosine-геометрия и совместимость между хостами не проверены.
Веса выбранных доноров нельзя произвольно переназначить или повысить.

## Строгое ограничение от совпадающих колонок

На всех1323 запросах хотя бы один правильный новый контакт встречался у
какого-либо другого активного source02-донора: доступность=1,0. Это
не гарантирует хорошего ранга при10 донорах.

Если два допустимых кандидата имеют в source02 одинаковые столбцы счётчиков
по всем активным донорам, любые неотрицательные веса дадут им одинаковый
голос. Их ничья ограничивает rank сверху даже при произвольной геометрии и
выборе доноров. Усреднив лучшую такую оценку для каждого запроса, получаем
сертифицированную **верхнюю границу MRR0,997784** по этой одной причине.
Она математически допустима и очень слаба: **не исключает MRR0,46**. Глобальная
оптимизация десятки и другие ограничения геометрии не сертифицированы.

## Бюджет score80 по сохранённым оценкам окон исходной модели

В каждом из окон14/15/16 условно заменены только Identity и New partners MRR
на одинаковые в этом ряду значения; Neighbors, Links, Pairs и их случайные
ориентиры сохранены как в `runs/original_codebook_recovery/test*.json`.
Сначала score каждого окна, затем их среднее. Это контрфактические числа,
не результат модели и не обещание что метрики могут сочетаться.

предполагает неизменную размерность/шансы и неизменные остальные метрики.

## Ограничения и следующий этап

Результат history0,317 показывает, что на уже изученном дне13 простое
историческое правило может выбрать полезные десятки с учётом его активной
когорты. Он **не демонстрирует перенос на новые дни или превращение в векторы**.
Нельзя сравнивать 0,317/0,482 с MRR лидера по дням14–16 как результат одной
модели. Результат зависит от выборки хостов; наблюдения зависимы и одно окно
не оценивает неопределённость между днями.

Следующий обязательный эксперимент: causal rolling-prefix, включая основу,
обученную до каждого прогнозируемого окна, и один общий допустимый набор
source-векторов. Сначала без доступа к labels сравнить хотя бы два окна,
потом измерить передачу полезных десяток в компактную cosine-геометрию и
все пять метрик. Нельзя дообучать на ответах дня13 или считать oracle-веса
историческими прогнозами.

Команда:

```
OPENBLAS_NUM_THREADS=2 OMP_NUM_THREADS=2 .venv/bin/python -m experiments.donor_diagnostics.run --output runs/donor_oracle_day13_new --queries 384
OPENBLAS_NUM_THREADS=2 .venv/bin/python -m pytest experiments/donor_diagnostics/test_run.py -q
```

Исходные данные и результаты — в PT_PROJECT_ML и runs. Первый запуск01 не
сохранил результаты из-за сериализации numpy.int64, повтор02 выполнен на128
хостах, окончательный03 — на384, без подбора по тестам14–16.
