# DC-SAGE: как реализовать на своих данных

Oct 26, 2026 · @Rodion

## 1. Что это и чего ожидать

**DC-SAGE** (directed contrastive SAGE) — нейросеть на графе, которая по потокам NetFlow строит вектор каждого хоста. Вектор складывается из профиля самого хоста и профилей его собеседников и обучается без разметки ролей. Этот документ — спецификация: по нему можно реализовать метод на своих данных, не обращаясь ко мне.

**Статус.** Метод описан, но не реализован и не запускался целиком. Цифр для него нет. Всё, что ниже названо «подтверждено», получено на упрощённых предшественниках.

**Что уже подтверждено** (LANL, день 02, окно train 1 час, test 30 минут, 2242 хоста; оценка кодом `evaluation` проекта PT-05):

- Добавить к профилю хоста усреднённые профили собеседников без обучения — Pairs AUC растёт с 0.923 до 0.985, Links AUC с 0.983 до 0.989, New partners MRR с 0.199 до 0.209. Neighbors@10 при этом падает с 0.247 до 0.232.
- Описывать хост гистограммой *ролей* собеседников (k-means, 2 шага) вместо списка собеседников: обучаемый прогноз связей 0.874 → 0.974, новые собеседники MRR 0.130 → 0.196. Узнаваемость при этом падает с 0.38 до 0.195.
- Существующий GraphSAGE проекта получил 13.2 балла. Причины: потеря на близость в случайных блужданиях, равномерное усреднение соседей (хабы доминируют), ненаправленный граф, 16 измерений.

**Зачем.** Метод должен давать три вещи из постановки проекта: поиск похожих хостов с объяснением, кластеры и подсветку аномальных переходов хоста между кластерами.

**Ограничения.** Сравнение шло на одном дне LANL; пилот с агрегатом соседей — на одном сиде. Эталон Neighbors построен из поведенческих признаков, поэтому измеряет «похожесть поведения», а не настоящую роль. Метрика «Neighbors» может падать при добавлении соседей: это компромисс, который нужно проверять, а не предполагать.

## 2. Данные и предобработка

На входе нужна таблица потоков NetFlow, из неё для каждого временного окна строятся направленный граф и признаки хостов. Окна нужно разделить по времени строго, иначе оценка будет завышена утечкой будущего.

### 2.1. Входные поля

| Поле | Что это | Поле LANL |
| --- | --- | --- |
| `ts` | начало потока, секунды | Time |
| `duration` | длительность, секунды | Duration |
| `src`, `dst` | хост — источник и получатель | SrcDevice, DstDevice |
| `proto` | протокол | Protocol |
| `src_port`, `dst_port` | порты | SrcPort, DstPort |
| `bytes`, `packets` | объём от источника | SrcBytes, SrcPackets |
| `resp_bytes`, `resp_packets` | объём ответа | DstBytes, DstPackets |

Если у вас другая сеть, приведите данные к этому виду. Обязательны `ts`, `src`, `dst`, `proto`, `dst_port`; остальные повышают качество поведенческого профиля. В LANL часть портов обезличена (строка `PortNNNNN`): её нужно брать как категорию, число из неё извлекать нельзя.

### 2.2. Временные окна

Разбиение как в таблице проекта PT-05 (поменяйте длительности под свою сеть, но порядок оставьте):

1. **train** — 1 час. Только на нём обучается всё: SVD, IDF, статистика нормировки и сама нейросеть. Для обучения его нужно разрезать на два среза по 30 минут: **S1** и **S2**.
2. **validation** — 30 минут после train. Подбор гиперпараметров.
3. **test** — ещё 30 минут. Смотрите один раз, после фиксации всех настроек.

Поток попадает в окно `[a, b)`, если `a <= ts` и `ts + duration < b`. Потоки, пересекающие границу, выбрасываются: иначе счётчики длинного потока утекут из будущего.

### 2.3. Когорта

Когорта — хосты, у которых в train не менее **300 событий** (потоки как src или dst, без потоков «в себя»). Когорта фиксируется по train до всех моделей. Хосты вне когорты всё равно остаются в графе как собеседники — они нужны, чтобы агрегат соседей был полным. Оцениваемые в окне хосты — когорта и активные в этом окне (в проекте — не менее 100 событий в test).

### 2.4. Граф окна

Для окна `w` постройте матрицу `C_w` размера N×N (разреженную): `C_w[u, v]` — число потоков с `src=u`, `dst=v` в этом окне. Диагональ обнулите. Две вещи важны:

- **Нумерация вершин единая** для всех окон (выберите словарь `host → индекс` по всем хостам, виденным в train, validation и test). Хосты, появившиеся только в позднем окне, получают новые индексы — и модель должна уметь их встраивать, то есть не полагаться на «ID как признак».
- **Рёбра направлены.** Оба направления нужны: `C_w` — исходящие связи, `C_w^T` — входящие.

### 2.5. Что должно лежать на диске после этапа

- таблица потоков каждого окна (`S1`, `S2`, `validation`, `test`), parquet или CSV;
- словарь `host → индекс` и список когорты;
- разреженная матрица `C` для каждого окна.

## 3. Признаки хоста

На вход сети подаётся вектор `x_v = [p_v ‖ b_v]`: профиль сервисов и ролей `p_v` (64 измерения) и поведенческий профиль `b_v` (около 30–60). **ID собеседников в признаках нет**: именно это позволяет сравнивать хосты без общих знакомых и встраивать новые хосты.

### 3.1. Профиль «сервис × роль» `p_v`

Идея взята из ветки `experiments/d&t` проекта PT-05 (файл `host_profile.py`). Каждый поток даёт по одному токену каждой стороне:

1. **Сервис** — меньший из двух портов, если он числовой и строго меньше 1024. Если такого нет, сервис = `other`.
2. **Роль** — сторона с портом-сервисом «сервер», другая «клиент»; при сервисе `other` роль `neutral`.
3. **Токен** — строка `proto/service/role`, например `6/443/client` у клиента и `6/443/server` у сервера.

Если порты у вас обезличены строками, примите единый правило: сервисом считается `dst_port`-строка, сервером — `dst`. Это допущение может ошибаться; отметьте его в отчёте.

```python
def tokens(f):                      # f: DataFrame потоков окна
    sp = pd.to_numeric(f.src_port, errors="coerce")      # NaN, если порт обезличен строкой
    dp = pd.to_numeric(f.dst_port, errors="coerce")
    dst_srv = (dp < 1024) & (sp.isna() | (dp < sp))     # dst — сервис (равенство → нейтрально)
    src_srv = (sp < 1024) & (dp.isna() | (sp < dp))     # src — сервис
    anon = sp.isna() & dp.isna()                        # оба порта обезличены: сервис = dst_port-строка
    svc = pd.Series("other", index=f.index)
    svc[dst_srv] = dp[dst_srv].astype(int).astype(str)
    svc[src_srv] = sp[src_srv].astype(int).astype(str)
    svc[anon] = "a:" + f.dst_port.astype(str)[anon]
    role_dst = np.where(dst_srv | anon, "server", np.where(src_srv, "client", "neutral"))
    role_src = np.where(src_srv, "server", np.where(dst_srv | anon, "client", "neutral"))
    pr = f.proto.astype(str)
    a = pd.DataFrame({"h": f.src.values, "t": (pr + "/" + svc + "/" + role_src).values})
    b = pd.DataFrame({"h": f.dst.values, "t": (pr + "/" + svc + "/" + role_dst).values})
    return pd.concat([a, b], ignore_index=True)   # groupby(["h","t"]).size() → матрица хост × токен
```

Далее: матрица счётчиков хост × токен → `log1p` → TF-IDF (`idf_t = log((N+1)/(df_t+1)) + 1`, где N — число хостов когорты, df — в скольких из них есть токен) → L2-нормировка строки → `TruncatedSVD(64)`. Словарь токенов, IDF и SVD обучаются **один раз на всём train-часе** и потом применяются к любому окну (в том числе к срезам S1 и S2). Новые токены в позднем окне пропускаются.

### 3.2. Поведенческий профиль `b_v`

В PT-05 это класс `BehavioralBaseline` (57 признаков). Если вы собираете своё, возьмите набор ниже; всё считается по окну отдельно и для каждой стороны (исходящая — хост был `src`, входящая — `dst`):

| Группа | Признаки |
| --- | --- |
| Объём | `log1p` числа потоков, байт, пакетов (in и out), средний размер потока, средняя длительность |
| Собеседники | `log1p` числа уникальных собеседников (in и out), доля исходящих связей в общем числе |
| Сервисы | число разных сервисов, что хост использует и что обслуживает; энтропия распределения по сервисам |
| Протоколы | доли TCP, UDP, ICMP, прочего |
| Время | доля потоков в каждом из 6 равных подокон, доля активных подокон, всплесковость `B = (σ − μ)/(σ + μ)` интервалов между потоками |
| Служебные | `log1p(число событий)` — по нему сеть узнаёт, насколько хосту можно доверять; флаг «в окне нет потоков» |

### 3.3. Нормировка и сборка

1. Всё с тяжёлыми хвостами — через `log1p`.
2. Среднее и разброс — по когорте train; z-score, обрезка на ±5. Храните эти числа вместе с моделью и применяйте к любому окну одинаково.
3. Хостам без потоков в окне: `x_v = 0` и флаг пустоты = 1.
4. `x_v = concat(p_v, b_v)`. Размерность входа `D_in` ≈ 100–120.

Хосты вне когорты (собеседники) получают те же признаки по тем же правилам, просто по меньшему числу событий; признак `log1p(число событий)` позволяет сети это учесть.

Выделенная ветвь — то, что добавляет граф; верхняя ветвь использует только профиль самого хоста. Нижние блоки показывают, где вектор нужен при обучении и после него.

### 4.1. Веса соседей (ослабление хабов)

Для отношения `r` — `out` или `in` — матрица смежности такая: `A_out = C`, `A_in = C^T`. Вес соседа `u` для хоста `v`:

```latex
a^{r}_{vu} = \log(1 + A_r[v,u]) \cdot \mathrm{idf}_u, \qquad
\alpha^{r}_{vu} = \frac{a^{r}_{vu}}{\sum_{u'} a^{r}_{vu'}}
```

Здесь `idf_u = log((N+1)/(df_u+1)) + 1`, где `N` — число хостов когорты в train, `df_u` — сколько хостов когорты общалось с `u` (в любом направлении). Для собеседника, не виденного в train, берётся максимальный `idf`. Хаб (сервер, с которым общается большая часть сети) получает `idf`, близкий к 1, редкий собеседник — большее.

**Выборка соседей.** При обучении для каждого хоста и отношения берётся `S1 = 25` соседей на первом слое и `S2 = 10` на втором; выбор с возвратом с вероятностью `α`. Тогда обычное среднее выбранных — несмещённая оценка взвешенного среднего. При выводе (без случайности) берётся 64 соседа с наибольшим `a`, веса перенормируются.

### 4.2. Слои

Размер скрытого состояния `H = 128`, выхода `d = 64`.

```latex
h^0_v = \mathrm{LN}(W_{in}\, x_v)
```

```latex
m^{l}_{r,v} = \sum_{u \in \mathcal{N}_r(v)} \alpha^{r}_{vu}\, h^{l-1}_u , \quad r \in \{out, in\}
```

```latex
h^{l}_v = h^{l-1}_v + \mathrm{Dropout}\Big(\mathrm{LN}\big(\mathrm{ReLU}(W^l_{self} h^{l-1}_v + W^l_{out} m^l_{out,v} + W^l_{in} m^l_{in,v} + b^l)\big)\Big), \quad l = 1, 2
```

Хост без соседей в данном направлении получает `m = 0`. LN — LayerNorm, веса `W` свои у каждого слоя и отношения; для всех окон модель одна и та же.

### 4.3. Выход и skip-связь

```latex
s_v = \mathrm{MLP}_{skip}(x_v), \qquad a_v = g(h^2_v), \qquad z_v = \frac{s_v + a_v}{\lVert s_v + a_v \rVert}
```

`MLP_skip` — `Linear(D_in, 256) → ReLU → Linear(256, d)`. `g` — `Linear(H, d)`, у неё **веса и смещение инициализируются нулями**. Поэтому в начале обучения `z_v` равен нормированному `MLP_skip(x_v)`: сеть стартует как метод на одном профиле и потом учится добавлять соседей. Если метод не добавляет пользы, он должен вернуться к уровню профильного бейзлайна — это нижняя граница по конструкции.

Раздельные векторы `s_v` («сам хост») и `a_v` («соседи») сохраняйте при выводе: по ним строятся объяснения сходства (раздел 6).

## 5. Обучение

Модель учится на одном train-часе двумя взаимно дополняющими потерями: контрастной («тот же хост в другой половине часа») и потерей на будущих связях. Разметка ролей не нужна.

### 5.1. Два представления каждого хоста

Разрежьте train на срезы **S1** и **S2** по 30 минут. Для каждого среза постройте свой граф `C_S1`, `C_S2` и свои признаки `X1`, `X2` (те же правила, та же модель TF-IDF/SVD и те же средние из train-часа). Дальше два прохода одной и той же сети дают `z¹` (по S1) и `z²` (по S2). В позитивы попадают только хосты когорты с не менее 30 событий в обоих срезах; остальные участвуют только как соседи.

### 5.2. Контрастная потеря (InfoNCE)

Пара `(z¹_v, z²_v)` — позитив, пары с другими хостами батча — негативы. Модель учится тому, что устойчиво у хоста во времени и отличает его от других.

```latex
\mathcal{L}_{nce} = \frac{1}{2B} \sum_{v \in batch} \Big[ \ell(z^1_v, z^2_\cdot) + \ell(z^2_v, z^1_\cdot) \Big], \quad
\ell(a_v, b_\cdot) = -\log \frac{\exp(a_v \cdot b_v / \tau)}{\sum_{u} m_{vu} \exp(a_v \cdot b_u / \tau)}
```

Здесь `τ = 0.1`, а `m_vu` — маска ложных негативов: `m_vu = 0` для `u ≠ v`, если косинус их профилей `p` выше 0.95, иначе 1. Без маски два одинаковых сервера в батче будут отталкиваться друг от друга, и роль размоется. Порог 0.95 — стартовый, проверьте на validation (чем ниже, тем больше хостов считаются «тождественными»).

### 5.3. Потеря на будущих связях

Эмбеддинги `z¹` (по S1) должны предсказывать рёбра S2. Декодер асимметричен, чтобы связь «клиент → сервер» не требовала сходства эмбеддингов:

```latex
s(u \to v) = (W_a z_u)^\top (W_b z_v) + \beta \log(1 + \deg_{in}(v)) + c, \qquad
\mathcal{L}_{link} = \mathrm{BCE}\big(\sigma(s), y\big)
```

`W_a`, `W_b` — матрицы 32×64, `β` и `c` — обучаемые числа (частота популярности сервера — сильный признак сам по себе, пусть он не загрязняет эмбеддинг). **Позитивы** — рёбра из `C_S2`; половину берите из рёбер, что были только в S2 (новые связи; без этого модель будет просто запоминать старые). **Негативы** — по 5 на каждый позитив: замена `v` на узел, выбранный с вероятностью пропорционально `степень^0.75`.

Итог: `L = L_nce + λ · L_link`, `λ = 0.3`.

### 5.4. Аугментации и масштаб

- **Dropout рёбер** 0.2 (на каждом шаге заново) и **dropout признаков** 0.1: чтобы модель не запоминала конкретные соединения.
- **Выборка соседей из раздела 4.1 не обязательна** на данных размера LANL (около 26 тысяч вершин, 165 тысяч рёбер за час): проще гонять весь граф целиком, оставив у каждого хоста не более 64 соседей с наибольшими весами `a`. Выборку подключайте, если вершин на порядок больше или не хватает памяти.
- Не забывайте: потери считаются только по хостам когорты, но в прямом проходе участвуют все вершины (собеседники тоже).

### 5.5. Скелет кода (PyTorch)

Полнографный вариант без выборки. Скелет не запускался; требуется `torch`, `scipy`, `numpy`.

```python
import numpy as np, scipy.sparse as sp, torch, torch.nn as nn, torch.nn.functional as F

def topk_rows(W, k):                       # оставить у каждой строки k наибольших весов (делать один раз)
    W = W.tocsr().copy()
    for i in range(W.shape[0]):
        s, e = W.indptr[i], W.indptr[i + 1]
        if e - s > k:
            d = W.data[s:e]; d[np.argsort(d)[:-k]] = 0
    W.eliminate_zeros()
    return W

def prepare_graph(C, idf, k=64):           # C: N×N, C[u,v] = число потоков u→v; вернёт (W_out, W_in) до нормировки
    res = []
    for M in (C.tocsr(), C.T.tocsr()):
        W = M.astype(np.float32); W.data = np.log1p(W.data)
        res.append(topk_rows(W @ sp.diags(idf.astype(np.float32)), k))
    return res

def norm_adj(W, drop=0.0, rng=None):       # dropout рёбер → построчная нормировка → torch.sparse
    W = W.copy()
    if drop > 0:
        W.data *= (rng.random(W.nnz) > drop); W.eliminate_zeros()
    rs = np.asarray(W.sum(1)).ravel()
    W = (sp.diags(1.0 / np.maximum(rs, 1e-9)) @ W).tocoo()
    idx = torch.tensor(np.vstack([W.row, W.col]), dtype=torch.long)
    return torch.sparse_coo_tensor(idx, torch.tensor(W.data), W.shape).coalesce()

class Layer(nn.Module):
    def __init__(s, H, p):
        super().__init__()
        s.fs, s.fo, s.fi = nn.Linear(H, H), nn.Linear(H, H, bias=False), nn.Linear(H, H, bias=False)
        s.ln, s.dr = nn.LayerNorm(H), nn.Dropout(p)
    def forward(s, h, m_out, m_in):
        return h + s.dr(s.ln(torch.relu(s.fs(h) + s.fo(m_out) + s.fi(m_in))))

class DCSAGE(nn.Module):
    def __init__(s, d_in, H=128, d=64, p=0.1):
        super().__init__()
        s.inp = nn.Sequential(nn.Linear(d_in, H), nn.LayerNorm(H))
        s.l1, s.l2 = Layer(H, p), Layer(H, p)
        s.skip = nn.Sequential(nn.Linear(d_in, 256), nn.ReLU(), nn.Linear(256, d))
        s.g = nn.Linear(H, d); nn.init.zeros_(s.g.weight); nn.init.zeros_(s.g.bias)   # старт = только профиль
    def forward(s, x, A_out, A_in):
        h = s.inp(x)
        for L in (s.l1, s.l2):
            h = L(h, torch.sparse.mm(A_out, h), torch.sparse.mm(A_in, h))
        sv, av = s.skip(x), s.g(h)
        return F.normalize(sv + av, dim=-1), sv, av

class Decoder(nn.Module):
    def __init__(s, d=64, r=32):
        super().__init__()
        s.a, s.b = nn.Linear(d, r, bias=False), nn.Linear(d, r, bias=False)
        s.beta, s.c = nn.Parameter(torch.zeros(1)), nn.Parameter(torch.zeros(1))
    def forward(s, zu, zv, logdeg_v):
        return (s.a(zu) * s.b(zv)).sum(-1) + s.beta * logdeg_v + s.c

def info_nce(a, b, false_neg, tau=0.1):    # false_neg: B×B bool, True — не считать негативом (без диагонали)
    lg = (a @ b.T / tau).masked_fill(false_neg, -1e9)
    t = torch.arange(len(a))
    return 0.5 * (F.cross_entropy(lg, t) + F.cross_entropy(lg.T, t))

def link_loss(z, dec, e_src, e_dst, neg_dst, logdeg):   # neg_dst: (len(e_src), 5)
    K = neg_dst.shape[1]
    pos = dec(z[e_src], z[e_dst], logdeg[e_dst])
    neg = dec(z[e_src].repeat_interleave(K, 0), z[neg_dst.reshape(-1)], logdeg[neg_dst.reshape(-1)])
    y = torch.cat([torch.ones_like(pos), torch.zeros_like(neg)])
    return F.binary_cross_entropy_with_logits(torch.cat([pos, neg]), y)

# цикл (сокращённо): W1 = prepare_graph(C_S1, idf); W2 = prepare_graph(C_S2, idf)
# на каждом шаге: A1 = [norm_adj(w, 0.2, rng) for w in W1]; A2 = [norm_adj(w, 0.2, rng) for w in W2]
#   z1, _, _ = model(X1 * feat_mask1, *A1);  z2, _, _ = model(X2 * feat_mask2, *A2)
#   loss = info_nce(z1[batch], z2[batch], fn_mask(batch)) + 0.3 * link_loss(z1, dec, e_src, e_dst, neg, logdeg)
#   loss.backward(); clip_grad_norm_(params, 1.0); opt.step()
```

### 5.7. Проверки во время обучения

1. **До обучения**: `z` должен равняться `normalize(MLP_skip(x))` (выход `g` — ноль).
2. **Коллапс**: средний попарный косинус `z` по батчу не должен стремиться к 1 (ориентир — ниже 0.5), а стандартное отклонение координат не падать в ноль.
3. **Вклад соседей**: следите за отношением `‖a_v‖ / ‖s_v‖`. Если оно остаётся почти нулём, модель соседей не использует, и метод выродился в профильный бейзлайн.

## 6. Использование: сходство, объяснения, кластеры, аномалии

После обучения веса замораживаются. Для любого нового окна делается один и тот же проход: потоки → граф и признаки по правилам разделов 2–3 (с сохранёнными SVD, IDF и статистикой нормировки) → `model(X, A_out, A_in)` без dropout и с top-64 соседями → `z`, `s`, `a`. Переобучение не нужно, новый хост встраивается так же.

### 6.1. Поиск похожих хостов

Ближайшие соседи по косинусу `z` (на тысячах хостов — прямое умножение матриц, на миллионах — FAISS). Для нового хоста считаем его `z` по его потокам и ищем ближайших среди уже известных.

### 6.2. Объяснение «почему они похожи»

Вектор `z` составлен из двух частей, поэтому для пары `(v, w)` считаются три числа:

| Число | Формула | Как читать |
| --- | --- | --- |
| Полное сходство | `cos(z_v, z_w)` | то, по чему ранжируем |
| Сходство «сами по себе» | `cos(s_v, s_w)` | похожи ли их сервисы и поведение |
| Сходство окружения | `cos(a_v, a_w)` | похожи ли типы их собеседников |

Для интерфейса: «похожи на 0.91: сервисы совпадают на 0.94, окружение на 0.72». Дополнительно покажите токены профиля `p` с наибольшим вкладом в общее (покомпонентное произведение TF-IDF-векторов над словарём токенов) и типы соседей: профили топ-5 собеседников с большими весами `a` у каждого из двух хостов. Примечание: косинусы частей не складываются в полный (полный — косинус суммы, не сумма косинусов), поэтому показывайте их как пояснение, а не как разложение.

### 6.3. Кластеры

HDBSCAN по `z` (`min_cluster_size` ≈ 10–20, метрика — евклидова на нормированных векторах, это эквивалентно косинусу). Шум (метка -1) не выбрасывать: это кандидаты на аномалии и нетипичные хосты. UMAP — только для картинки в интерфейсе. Каждый кластер описывается тремя вещами: топ-токены среднего профиля `p` членов, средние значения поведенческих признаков и доля связей внутри кластера и между кластерами.

### 6.4. Аномалии переходов между кластерами

Для хоста `v` в соседних окнах `t` и `t+1` считаются три сигнала:

1. **Дрейф**: `d_v = 1 − cos(z_v^t, z_v^{t+1})`. Обучение явно научило модель приближать тот же хост в соседних срезах, поэтому нормальный `d_v` мал. Калибровка: считайте `d_v` для пары срезов S1→S2 на когорте train (это «нормальный дрейф») и на нем же паре validation → test — это уже честная проверка. Хост считается подозрительным, если `d_v` выше 99-го процентиля нормального распределения в его кластере; порог выбирайте по допустимой доле ложных тревог.
2. **Смена кластера с запасом**: кластер в `t+1` другой, и хост ближе к новому центру, чем к старому, с разницей не менее маржи (выбрать по validation), чтобы не ловить хосты на границе.
3. **Неожиданные связи**: связи в `t+1`, для которых декодер выдаёт низкую вероятность `σ(s(u→v))`. Добавляйте их в карточку аномалии как объяснение: кто новый собеседник и по какому сервису.

Разметки атак в данных нет, поэтому качество таких алертов смотрится инъекциями (раздел 7).

## 7. Оценка

Разметки ролей нет, поэтому качество меряется косвенно: насколько эмбеддинг из раннего окна помогает предсказывать позднее поведение. Только так и можно сравнивать методы, не выдумывая роли. Ниже список метрик PT-05; если у вас есть этот репозиторий, берите готовый код из `evaluation/` и `scoreboard/`.

### 7.1. Протокол без утечек

1. Окна train → validation → test не пересекаются; потоки на границе выбрасываются.
2. Всё обучаемое — TF-IDF, SVD, IDF собеседников, статистика нормировки, веса сети — учится только на train. Внутри train срез S2 не должен попадать в признаки S1.
3. Когорта определяется по train до обучения.
4. Гиперпараметры и остановка — по validation. Test смотрится один раз для зафиксированной конфигурации.
5. Для проверки будущего эталоны строятся по более позднему окну, а эмбеддинг считается по раннему.

### 7.2. Метрики

| Метрика | Что проверяет | Как считается |
| --- | --- | --- |
| Neighbors@10 | у близких векторов похожее поведение | доля совпадения 10 ближайших по эмбеддингу с 10 ближайшими по эталонным признакам целевого окна |
| Links AUC | по двум векторам можно предсказать, будет ли трафик между хостами | ROC-AUC по парам хостов целевого окна; считайте и по косинусу, и по обученному на validation классификатору поверх эмбеддингов; для DC-SAGE ещё по декодеру `s(u→v)` |
| New partners MRR | похожие хосты подсказывают новых собеседников | для хоста A берём k ближайших, собираем их прошлых собеседников (вес = косинус × число контактов), ранжируем, мерим MRR на тех, кто у A в целевом окне новый |
| Pairs AUC | хосты с общими собеседниками близки | позитив — жаккар множеств собеседников выше порога, негатив — жаккар равен 0 |
| Identity Top-1 | тот же хост узнаётся через некоторое время | доля хостов, чей эмбеддинг train ближайший среди всех по эмбеддингу test этого же хоста |

Общий score PT-05 — среднее геометрическое четырёх задач (Behavior, Future links, Shared partners, Identity), каждая переведена в шкалу 0–100 (0 — случайный уровень, 100 — идеал). Провал одной задачи тянет весь балл вниз. Интервалы — bootstrap по хостам (не по парам).

**Предупреждение об эталоне.** Эталон Neighbors построен из поведенческих признаков целевого окна, поэтому методы на поведенческих признаках получают тут бонус. В отчёте пишите: «лучше на этом эталоне», а не «находит роли».

### 7.3. Бейзлайны и абляции

Всё ниже обучается на тех же данных и выводит тот же размер эмбеддинга `d`:

| Вариант | Что меняется | Что проверяет |
| --- | --- | --- |
| `random` | случайные векторы | нижний ориентир |
| профиль `p` → SVD | без нейросети, без графа | то, что даёт `d&t` |
| `behavioral` (`b`) | без графа | то, что даёт поведенческий профиль |
| `skip-only` (граф выключен, `g` ≡ 0) | обученный MLP по `x` с теми же потерями | **нижняя граница метода**; если DC-SAGE не лучше её, граф не нужен |
| линейный агрегат | `x_v ‖ 0.5 · mean_neighbors(x)` без обучения | обучаемый энкодер обязан быть лучше простого усреднения |
| без направления | `A_in` и `A_out` объединены | нужны ли два типа рёбер |
| без IDF | `idf_u = 1` | даёт ли ослабление хабов что-то |
| без контрастной потери | только `L_link` | нужна ли InfoNCE |
| без потери связей | `λ = 0` | нужен ли декодер |
| без маски ложных негативов | `m_vu ≡ 1` | мешают ли дубликаты ролей |
| 1 слой вместо 2 | убрать `l2` | нужны ли соседи соседей |
| `hybrid_tfidf` проекта | готовый лидер таблицы (45.3) | нужен ли вообще DC-SAGE, если гибрид уже есть |

Для всех обучаемых вариантов — 5 сидов, отчёт «среднее ± отклонение». Разница меньше разброса между сидами — не разница.

### 7.4. Протокол «новый хост»

Исключите случайные 30% хостов когорты из обучения целиком: удалите их потоки, рёбра и обозначения собеседников из train-графа, из IDF и из SVD. После обучения встройте их по их же потокам и замерьте Neighbors@10 и New partners для них. Это прямая проверка требования «для нового хоста показать, на кого он похож». Нейросеть могла запомнить обучающие хосты, поэтому этот протокол честнее обычного.

### 7.5. Проверка аномалий инъекциями

Разметки атак нет, поэтому в test-окно вносятся искусственные изменения для случайных 5% хостов, а метод должен их найти:

- **Смена роли**: потоки хоста заменяются потоками случайного хоста из другого кластера.
- **Сканер**: хост обращается к сотням случайных хостов на один порт.
- **Безобидное изменение**: активность хоста увеличивается в два раза (потоки повторяются). Тревоги на неё — ложные.

Метрика: ROC-AUC дрейфа `d_v` «внедрённые против нормальных» и «безобидные против нормальных». Хороший результат — первый AUC высокий, второй близок к 0.5. Сравнивайте с бейзлайном «расстояние между профилями `x` двух окон».

### 7.6. Критерии успеха (задайте до запуска)

1. Ни одна из четырёх задач не хуже `skip-only` больше чем на доверительный интервал.
2. Хотя бы одна из задач Future links, Shared partners лучше, причём интервалы не пересекаются с `skip-only`.
3. Падение Neighbors@10 относительно `skip-only` — не более 0.02.
4. Обученный энкодер не хуже линейного агрегата по общему score.

Если критерии 1–4 не выполняются, значит графовая часть на ваших данных не оправдана, и такой результат тоже нужно записать в отчёт. Пороги — мои предложения, а не доказанные нормы.

## 8. Пошаговый план и риски

Делайте по порядку: каждый шаг заканчивается проверкой, без которой следующий не имеет смысла. Время на шаги я не оцениваю, это зависит от ваших данных.

1. **Подготовить данные** (раздел 2): окна train/validation/test, когорта, словарь хостов, матрицы `C`, срезы S1/S2. *Проверка:* число потоков и хостов когорты в каждом окне сходится с тем, что вы ожидаете; потоки без пересечения границ.
2. **Собрать признаки** (раздел 3): `p_v`, `b_v`, нормировка. *Проверка:* без нейросети посчитайте метрики для профиля `p` и `b` по отдельности — это бейзлайны и проверка стенда оценки.
3. **Подключить оценку** (раздел 7). *Проверка:* случайные векторы дают случайный уровень (AUC близок к 0.5, Top-1 около 0).
4. **Реализовать `skip-only`**: тот же `DCSAGE` с `g ≡ 0` и обучением на обеих потерях. *Проверка:* потеря падает, коллапса нет (раздел 5.7), метрики не хуже профильных бейзлайнов.
5. **Включить граф**: разморозить `g` и слои сообщений. *Проверка:* сравните с `skip-only` и с линейным агрегатом; работайте на validation.
6. **Добавить потерю на связях и маску ложных негативов**, подобрать гиперпараметры (раздел 5.6).
7. **Зафиксировать конфигурацию и один раз прогнать test**, 5 сидов, абляции, протокол «новый хост» и инъекции (раздел 7).
8. **Собрать продукт** (раздел 6): поиск похожих, объяснения, кластеры, аномалии.

### Риски

| Риск | Как увидеть | Что делать |
| --- | --- | --- |
| Граф не даёт пользы сверх профиля | `‖a‖/‖s‖` близок к нулю, метрики как у `skip-only` | увеличить вес потери на связях, проверить что у вас вообще есть сигнал в соседях (линейный агрегат) |
| Контрастная потеря убивает похожесть ролей | Neighbors падает, но Identity растёт | понизить порог ложных негативов, повысить температуру τ |
| Роли теряют узнаваемость | Identity Top-1 ниже бейзлайна без графа | в нашем пробном эксперименте с кластерными ролями она упала вдвое; здесь защита — skip-связь и InfoNCE, но проверять надо |
| Тот же день — один день | результат не воспроизводится на другом дне | сразу прогнать несколько дней и отчитываться по каждому |
| Эталон Neighbors круговой | методы на поведенческих признаках выигрывают «бесплатно» | не делать выводов о «ролях», только о совпадении с эталоном; добавить независимый эталон, если появится |
| Обезличенные порты искажают профиль | много редких токенов «сервиса» | отбросить токены в менее чем двух хостах (`min_df = 2`) |
| Нехватка памяти на большой сети | падает полнографный проход | перейти на выборку соседей из раздела 4.1 и мини-батчи по узлам |
