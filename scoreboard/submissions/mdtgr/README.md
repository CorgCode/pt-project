# MD-TGR: многодневный temporal graph retriever

## Кратко

Метод учится на последовательности дней и строит вектор хоста из трёх блоков: поведения текущего окна,
персонального кода хоста (один на всю историю) и обучаемого графового блока дня. Партнёрский лосс
написан ровно по формуле метрики «новые собеседники», поэтому обучение напрямую двигает MRR, а
персональный код держит узнаваемость через время.

## Архитектура

Вектор — конкатенация трёх блоков, веса блоков перебираются на validation без переобучения:

1. **anchor** — поведенческий профиль train-окна (57 чисел: порты, протоколы, направления, байты,
   энтропии, доли). Именно он лежит в `embeddings.csv`, по которому считаются Behavior, Future links,
   Shared partners и Pairs, поэтому он же — вход модели при обучении.
2. **code** — латентный код хоста, один на всю историю 02–12 (64 числа). Он одинаков во всех окнах,
   поэтому и даёт узнаваемость; обучается только партнёрским лоссом — то есть кодирует «с кем этот
   хост обычно сходится».
3. **window** — нейросетевой блок окна: поведение в общей системе координат, контакты с партнёрами
   в обе стороны и сервисы (протокол, порт) через EmbeddingBag, затем два слоя message passing по
   ненаправленным рёбрам host–host. Он ловит изменения дня ко дню.

Итоговая размерность 57 + 64 + 96 = 217. Голова окна — MLP на 96 чисел, косинус считается по
итоговому вектору.

## Данные

Поля потоков: `src`, `dst`, `dst_port`, `proto`, `bytes`, `packets`, `ts` (+ `duration`, `resp_bytes`
для поведенческого профиля и весов рёбер). Тем самым используется всё, что даёт pipeline: связи,
сервисы и поведение.

Словари партнёров, сервисов, портов и протоколов фиксируются **только по train-окну** (день 02) и не
меняются; имена и сервисы, впервые появившиеся позже, попадают в «неизвестные» — утечки из поздних
окон нет. Петли в контакты и рёбра не входят. Для каждого дня строится свой срез, модель одна и та же,
поэтому системы координат общие (`SHARED_COORDINATES`).

## Обучение и подбор

Эпизод обучения — «train → день d»: матрица старых контактов `M` всегда из train-окна (так устроена
метрика), цель — новые собеседники дня `d`. Лосс:

    s(A, c) = Σ_B w(A, B) · M[B, c],   w — top-10 косинусных соседей A, обрезанные снизу нулём
    L = logsumexp_c s(A, c) − logsumexp_{c ∈ targets} s(A, c)

Это listwise-суррогат ранга (MRR); старые собеседники и сам хост замаскированы, как в метрике.
Счётчики сжимаются `log1p` и центрируются по строке — ранжирование от этого не меняется, но градиент
устойчив. Дополнительно — небольшой BCE на косинусе для новых рёбер дня.

Протокол: обучение по дням 02–12, контроль (dev) — день 13, дни 14–16 не участвуют ни в обучении, ни
в подборе (окна различаются по времени, а не по имени; есть отдельный тест). Веса трёх блоков
перебираются на validation официальной функцией `evaluation.submit.validation_score`.

Признаки модели всегда берутся из train-окна — того же, что попадает в `embeddings.csv`. Окно дня
используется только для вектора Identity. Иначе модель училась бы читать связи из графа дня, которого
в отправке нет.

Полный прогон, включённый в scoreboard, набрал **60.5** в среднем за дни 14–16
(60.9 / 60.7 / 59.9). Размерность вектора — 217.

Ниже результаты отдельного пилотного прогона, обученного на короткой истории:

| Вариант | Число |
|---|---|
| anchor-only, validation score | 44.15 |
| MD-TGR (эпизоды 02–04, dev 05), validation score | 58.07 при весах `(1.5, 1.0, 0.5)` |
| Test-score пилотной модели, веса выбраны на validation | **65.26** |

В пилотном прогоне: Behavior 74 (в среднем по окнам), Future links 28, Shared partners 98,
Identity 87. Для сравнения, `behavioral` берёт Identity 22, а `multiday_codebook_plus` — 60 при
Future links 46. Это сравнение относится к пилотному прогону.

## Ограничения

- Код хоста — таблица на когорту: при смене когорты метод нужно переобучать, «дообучить нового хоста»
  без его истории нельзя.
- Узнаваемость проверена через Procrustes на половине хостов (как в официальной метрике); вклад
  блоков подобран на validation, а не на test-днях.
- Вектор `embeddings.csv` строится из train-окна; вектор дня (для Identity) — из потоков самого окна.
  Это разрешено и так же устроен поведенческий эталон, но означает, что Identity-вектор зависит от
  трафика соответствующего дня.
- Для повторения полного прогона нужны окна дней 02–16. Инструкции в [README метода](../../../methods/mdtgr/README.md).
