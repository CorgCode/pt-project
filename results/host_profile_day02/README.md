# Эксперимент с host_profile.py — LANL day 02

Дата: 19 октября 2026. База репозитория: `e086884`.

Выбранный на validation профиль **TF-IDF + роль клиента/сервера + SVD-32 без центрирования**
получил на test **33,38 балла**, третье место при добавлении к опубликованной таблице.
Его сильная сторона — узнаваемость хоста: **31,63% Top-1** против 19,98% у
`node2vec_services`, лучшего опубликованного метода по этой метрике.
По соседям и прогнозу связей профиль заметно уступает лидирующему гибриду.

Это результат на одном дне и конкретных окнах. Разметки ролей хостов нет:
этот эксперимент не устанавливает, что модель восстанавливает настоящие роли компьютеров.

когорты по каждому окну и списки оцениваемых хостов.

## Как строились векторы

Основа — исходный `host_profile.py`, оставленный без изменений.
Добавлен `methods/aggregated_host_profile.py`, повторяющий его вычисления по
счётчикам `(host, token, 1800-секундное окно)`.
Сначала суммируются счётчики всех чанков, затем применяется `log1p`:
разбиение CSV на чанки не меняет результат.
Численное совпадение с исходной моделью проверено для всех семи вариантов.

1. Каждый поток даёт токен каждой стороне: протокол, сервис и роль в обмене.
2. Сервис — меньший числовой порт, если он строго меньше 1024. Его сторона считается
   сервером, другая — клиентом; равные/высокие порты дают нейтральную роль.
3. Для каждого хоста считаются частоты токенов по 30-минутным окнам.
4. У выбранного варианта применяется `log1p`, IDF по train-хостам и L2-нормировка.
5. SVD обучается только на train, размерность 32, `seed=0`.
6. Проекция и итоговая L2-нормировка одинаковы для всех окон.

В исходной формуле деление на число активных окон является скаляром для строки
и при последующей L2-нормировке сокращается. На результат влияет применение
`log1p` внутри окон; это не усреднение отдельно нормированных векторов окон.

Опциональный skip-gram не включён: нужны последовательности контекстов и отдельная
процедура обучения/выравнивания между окнами. Данный прогон проверяет профиль,
веса, направление и блок структуры соседей; это не полная проверка всех идей файла.

## Выбор по validation

Критерий зафиксирован до результатов: максимум `partner_new_mrr` — новые собеседники
через похожих хостов. Он выбран как проверка на будущих связях, отдельная от эталона
сходства сервисных профилей. Всего проверено 7 конфигураций.

| вариант | размерность | Соседи@10 | новые собеседники MRR | пары AUC | узнаваемость Top-1 |
|---|---:|---:|---:|---:|---:|
| raw, без ролей | 32 | 0,0963 | 0,2291 | 0,9096 | 0,1496 |
| raw, роли | 32 | 0,1099 | 0,2293 | 0,9368 | 0,1615 |
| log + L2, роли | 32 | **0,1116** | 0,2420 | **0,9854** | 0,2337 |
| TF-IDF, без ролей | 32 | 0,0913 | 0,2466 | 0,9730 | 0,2339 |
| **TF-IDF, роли — выбран** | 32 | 0,1027 | **0,2500** | 0,9772 | 0,2265 |
| TF-IDF, роли, центрирование | 32 | 0,1030 | 0,2413 | 0,9422 | 0,2236 |
| предыдущий + структура × 0,5 | 37 | 0,1066 | 0,2417 | 0,9642 | **0,2563** |

Выбор сохранён в [selection.json](selection.json) до чтения test-профиля моделью
и до оценки test. Подготовка агрегатов всех окон проведена заранее без использования
значений метрик для выбора конфигурации. Полные интервалы:
[validation.md](validation.md), [metrics/validation](metrics/validation).
Общий балл validation не является критерием выбора: там ещё недоступен обученный
классификатор связей, для которого нужен более ранний целевой эталон.

## Итоговый test

Выполнен один финальный прогон выбранной конфигурации. Остальные шесть профилей
на test не сравнивались. Все штатные метрики доступны, кроме зонда по внешним
меткам: `labels.csv` отсутствует.

| метрика | host_profile, 32 | behavioral, 57 | node2vec_services, 32 | hybrid_services, 105 |
|---|---:|---:|---:|---:|
| балл | **33,38** | 31,04 | 23,78 | 35,41 |
| Соседи@10 | 0,1188 | 0,2693 | 0,0878 | 0,2585 |
| Связь, обученный AUC | 0,9471 | 0,9832 | 0,8221 | 0,9936 |
| Новые собеседники MRR | 0,2178 | 0,2041 | 0,1814 | 0,2353 |
| Пары AUC | 0,9635 | 0,9541 | 0,9057 | 0,9530 |
| Узнаваемость Top-1 | **0,3163** | 0,1035 | 0,1998 | 0,1624 |

Точные значения всех сравнений — [comparison_test.csv](comparison_test.csv);
готовая таблица — [comparison_test.md](comparison_test.md).
Бейзлайны взяты из опубликованных JSON, заново не обучались.
Штатная проверка совместимости подтвердила одинаковые отпечатки эталонов,
обучающего эталона классификатора, когорты, типа данных и split.
Размерности методов различаются; прямое сравнение при 32 измерениях есть
с `node2vec_services`, но не с гибридом из 105 признаков.

95% интервалы выбранного профиля, 200 bootstrap-повторов:

- Соседи@10: 0,1111–0,1264.
- Связь, обученный AUC: 0,9257–0,9591.
- Новые собеседники MRR: 0,1991–0,2338.
- Пары AUC: 0,9481–0,9728.
- Узнаваемость Top-1: 0,2863–0,3403.

Узнаваемость в основной таблице посчитана с Procrustes, как у опубликованных методов:
1 121 хост для выравнивания и 1 121 для проверки/галереи.
Без выравнивания Top-1 равен 0,3172: результат сохраняется в общей системе координат.
Это не поиск среди всех 6 453 train-хостов.

Косинус профилей как прямой прогноз связи даёт AUC **0,1906**, а новых связей — 0,1878.
Схожесть роли нельзя использовать как вероятность непосредственной связи:
клиент и сервер могут общаться, имея разные профили.
Для AUC 0,9471 штатный LogisticRegression обучен на парах validation,
а эмбеддинги для его обучения и теста в обоих случаях взяты из train.

## Практический вывод

Профиль стоит сохранить как быстрый базовый метод и кандидат на компонент гибрида:
при 32 координатах он заметно улучшает узнаваемость и даёт конкурентный общий балл.
Этот прогон не показал универсального преимущества TF-IDF над log:
у log выше сходство соседей и AUC пар на validation; интервалы MRR вариантов перекрываются.
Центрирование по умолчанию включать оснований нет: оно ухудшило выбранный MRR на validation.

Следующий независимый эксперимент — тот же замороженный профиль на другом дне,
затем сравнение при одинаковой размерности и проверка добавления профиля в гибрид.
Числовые сервисные порты >=1024 (например 5432, 8080) сейчас теряются в общем
нейтральном токене: расширять их обработку следует отдельной абляцией с новым validation,
а не подбирать по уже просмотренному test.
Проверен один seed; bootstrap-интервалы описывают разброс по хостам,
а не по переобучениям SVD или по дням.

## Где файлы и как повторить

Эмбеддинги находятся локально в
`runs/host_profile/submissions/host_profile_tfidf_directed/`:

- `embeddings.csv` — все 6 453 хоста, **train**-векторы для оценки будущего;
- `validation.csv`, `test.csv` — векторы этих окон для узнаваемости;
- `SHARED_COORDINATES` — декларация общей системы координат;
- `provenance.json` — обучение только на train.

Формат: `host_id,emb_0,...,emb_31`, строки без повторов, значения конечны.
Названия колонок исходных подготовленных потоков переводятся так:
`ts → time`, `src_port → sport`, `dst_port → dport`.

Важно: CLI исходного `host_profile.py` записывает в `embeddings.csv` векторы позднего
окна, а штатный оценщик ожидает в нём **train**-векторы.
Адаптер устраняет это несовпадение. Просто отправлять исходный CLI-файл в таблицу нельзя:
оценка прогноза будущего получила бы трафик из будущего.

```bash
# Численное совпадение с исходным методом, неизвестные токены, неизменность fit.
.venv/bin/python -m pytest -q methods/test_host_profile.py

# Для нового прогона нужен новый каталог.
.venv/bin/python -m experiments.host_profile_experiment prepare --out-dir runs/profile_repeat
.venv/bin/python -m experiments.host_profile_experiment run --out-dir runs/profile_repeat

# Только формат уже готового файла.
.venv/bin/python -m evaluation.validate runs/host_profile/submissions/host_profile_tfidf_directed/embeddings.csv
```

Зависимости численной части уже имелись в системном Python. Для полного набора
тестов установлен `matplotlib` в локальную `.venv` с доступом к системным пакетам.
Версии и контрольные суммы: [environment.json](environment.json).
Полный набор проверок: **422 passed, 6 skipped**, включая 8 тестов нового адаптера.
Восстановление/агрегирование заняло около 46 секунд, семь оценок validation и одна
test — около 138 секунд, включая bootstrap; агрегаты занимают около 21 МБ.
Результаты не отправлялись в GitHub или внешние сервисы, общая таблица репозитория не изменена.
