# MD-TGR — передача тимлиду

Многодневный метод для scoreboard: обучение по дням 02–12, контроль (dev) — день 13, итог — дни 14–16.
Карточка метода: `scoreboard/submissions/mdtgr/README.md`.

## Коротко: что делать

```powershell
# 1. Подготовить многосуточные окна (нужны raw-файлы дней 02–16)
python -m pipeline.prepare run `
  --netflow C:\path\raw\netflow_day-02.bz2 ... C:\path\raw\netflow_day-16.bz2 `
  --config methods/mdtgr/configs/full_days_02_16.json `
  --output-dir C:\path\processed_mdtgr --overwrite

# 2. Собрать срезы (один .npz на окно + словари + manifest.json)
python -m methods.mdtgr.shards --processed C:\path\processed_mdtgr --out C:\path\mdtgr_shards

# 3. Всё остальное — одним раннером: обучение, подбор весов, отправка, оценка
$env:PT_DATA = 'C:\path\processed_mdtgr'
python scoreboard/mdtgr.py
```

Раннер кэширует срезы в `scoreboard/submissions/mdtgr/.build/` (каталог в .gitignore), кладёт
чекпойнты и `weights.json` туда же, пишет векторы в `scoreboard/submissions/mdtgr/` и вызывает
`evaluation.submit.score`. Повторный запуск без `--rebuild-shards` не пересобирает срезы.

Флаги раннера: `--epochs` (по умолчанию 40), `--anchors` (1024; на слабой машине 256–512),
`--seed`, `--rebuild-shards`, `--no-tune` (не перебирать веса блоков), `--no-score` (только обучить).

## Протокол (объявлен заранее)

| Роль | Окна | Что происходит |
|---|---|---|
| источник `M` | `train` (день 02, 11:00–12:00) | старые собеседники; словари тоже только отсюда |
| **признаки модели** | `train` | тот же вектор, что уходит в `embeddings.csv` |
| эпизоды | `test_day02` … `test_day12` (12:30–13:30) | цели дня `d` при признаках train; `M` всегда train |
| dev | `test_day13` | выбор чекпойнта, в обучение не входит |
| подбор весов блоков | `validation` (день 02, 12:00–12:30) | `evaluation.submit.validation_score` |
| итог | `test`, `test_day15`, `test_day16` | только оценка |

**Важно про признаки.** 4 из 5 метрик scoreboard считаются по `embeddings.csv`, то есть по вектору
train-окна; окно дня используется только для Identity (`test.csv` / `test_dayNN.csv`). Поэтому эпизод —
это «признаки train → цели дня `d`» (`build_episode(..., features="train")`). Если брать признаки самого
дня `d`, модель учится читать новые связи из графа, которого в `embeddings.csv` на тесте не будет, и NPR
не переносится. Это исправление протокола зафиксировано в `train.py`.

Дни 14–16 отсекаются **по времени окна** (`OFFICIAL_TEST_START = 1168200.0` = 14-й день 12:30), а не
по имени: окно с именем `test` в другой день в обучение попадёт, а официальный день 14 — нет.
Это закреплено тестом `methods/mdtgr/test_runner.py`.

Веса блоков `(anchor, code, window)` — не параметры обучения, а настройки вывода: перебираются на
validation после обучения (сетка 3×3×3, `weights.json`), test-дни в подборе не участвуют.

## Устройство

- `features.py` — поведенческий профиль (57 чисел) и `Schema`: свои нормировки по окну (`behavior`,
  якорь) и в train-системе координат (`beh_shared`, вход модели).
- `shards.py` — срезы окон: контакты в обе стороны (счётчики и байты), сервисы (протокол, порт),
  рёбра host–host, маска оцениваемых хостов. Словари — только по train. `hosts.txt` — порядок строк.
- `dataset.py` — чтение срезов, тензоры окна, матрицы метрики `M`/`T` и позиция «сам хост» среди
  кандидатов.
- `model.py` — `anchor ⊕ code ⊕ window`, EmbeddingBag, два слоя message passing, `compose` с весами.
- `losses.py` — партнёрский listwise-лосс (ровно формула метрики), BCE на рёбрах, InfoNCE между днями.
- `train.py` — эпизоды, guard на официальные test-окна, чекпойнты, dev-метрика.
- `infer.py` — векторы для отправки, подбор весов на validation.
- `evaluate.py` — локальная копия механики «новые собеседники» для dev (сверена с эталоном).

## Что проверено локально

Данные: `pipeline.prepare` по дням 02–05 (когорта 6453; оцениваемых validation 2761, test 5445,
`test_day03` 5015, `test_day04` 5239, `test_day05` 4171). Официальные test-окна (`test`,
`test_day15`, `test_day16`) собраны из эталонного `processed`, порядок хостов совпал с официальным.

- Срезы официального `processed` совпадают с эталоном `reference/validation/partners.csv`:
  `M`, `T` и новые цели — max diff `0.0`, nnz 195348 / 153115 / 14201; `eval_hosts` = pool (2761).
- `methods/mdtgr/evaluate.new_partner_metrics` совпадает с `evaluation.partners.partner_ranking`
  (view «new») на синтетике и на официальном validation (тесты `test_metric.py`).
- **Локальный harness воспроизводит официальную оценку.** Anchor-only через `evaluation.submit.score`
  даёт ровно метрики `behavioral` по consistency@10 (0.2929 / 0.2519 / 0.1255), NPR
  (0.1249 / 0.1198 / 0.2869) и pairs (0.981). Значит, локальные числа можно сравнивать с таблицей.
- `pytest methods/mdtgr` — 27 тестов: словари только по train, контакты неориентированные без петель,
  матрицы = эталон, метрика = эталон, лоссы, сохранение/загрузка, экспорт, guard, обучение на синтетике.

## Ресурсы и время

Локально (8 CPU, 16 ГБ, без GPU) обучение на срезах официального размера идёт на CPU; GPU не нужен,
но пригодится. По памяти: срезы 6453 хостов × 26135 партнёров, все эпизоды держатся в памяти —
несколько гигабайт; при нехватке RAM уменьшайте `bag_dim`/`hidden` и число эпизодов.

Полный прогон по дням 02–12 на CPU — ориентировочно единицы часов (12 эпизодов × 40 эпох × 256
якорей); на GPU быстрее. `epochs` можно снизить до 25–30 без большой потери.

## Ограничения

- Дни 03–13 нужны как отдельные окна `test_dayNN` (12:30–13:30) в `processed`; если их нет, раннер
  честно падает с «нужны хотя бы два дня до официального test».
- Код хоста — таблица на когорту: при другой когорте нужно переобучение.
- Веса блоков подбираются на validation (день 02). Дни 14–16 используются для итоговой оценки.
